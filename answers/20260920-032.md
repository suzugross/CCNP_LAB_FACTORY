## 解説

### 完成文: DMVPN を守る IPsec の連鎖(IKEv2 + IPsec プロファイル)

```
crypto ikev2 proposal PROP-NGE
 encryption aes-gcm-256
 prf sha384
 group 19
crypto ikev2 policy POL-NGE
 proposal PROP-NGE
crypto ikev2 keyring KR-DMVPN
 peer ANY
  address 0.0.0.0 0.0.0.0
  pre-shared-key Dmvpn-Psk-77
crypto ikev2 profile IKEV2-DMVPN
 match identity remote address ［①］0.0.0.0
 authentication remote pre-share
 authentication local pre-share
 keyring local KR-DMVPN
 dpd 30 5 on-demand
crypto ipsec transform-set TS-GCM esp-gcm 256
 mode ［②］transport
crypto ipsec profile DMVPN-PROF
 set transform-set TS-GCM
 set pfs group19
 set ikev2-profile IKEV2-DMVPN
!
interface Tunnel0
 tunnel protection ipsec profile DMVPN-PROF
```

オブジェクトは **［③］proposal → policy → keyring → ikev2 profile → ipsec profile → tunnel protection** の順に参照される。keyring と profile を **［④］スポーク間直接通信の相手 NBMA が事前に分からない** ため wildcard にしている。ピアごとにアドレスを絞ると hub-spoke は正常でスポーク間の直接通信だけ成立せず、通信自体はハブ折返しで通り続けるので、症状が hub-spoke 間に出ず気づきにくい(実測)。transform-set を **［②］transport** にするのは GRE で外側 IP ヘッダが既に付いており、tunnel モードの外側 IP 20 バイトが無駄になるからで、両端で食い違っても不通にはならず Tunnel モードに合意して上がる(実測)。set ikev2-profile を書き忘れると **［⑤］IKEv1(ISAKMP)にフォールバックし、ポリシーが無いので SA が上がらない**。dpd は相手の死活監視(Dead Peer Detection) で、IPsec で保護したトンネルでは GRE キープアライブの代わりになる。crypto map と違い、この方式ではどのトラフィックを暗号化するかの ACL が要らず、Tunnel を通る全パケットが対象になる。
