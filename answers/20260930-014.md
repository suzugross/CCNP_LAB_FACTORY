## 解説

### 完成文: オーバーレイ運用の罠: 再帰ルーティング・map multicast の引数・shared・protection 変更

トンネルの宛先(NBMA)への経路をトンネル自身から学ぶと再帰ルーティング(トンネルが自分の中を通ろうとして落ちる) になる。p2p GRE では **［①］%TUN-5-RECURDOWN** が出て Tunnel が周期的に落ちるが、mGRE ではこのログが出ず、約 15 秒周期の EIGRP 隣接フラップと `show ip route <NBMA>` が via Tunnel0 になることで見抜く(実測)。原因の典型はハブが underlay の網をクラスフルな network 文でオーバーレイの IGP に広告してしまうことで、対策は **［②］underlay の経路をオーバーレイの IGP に入れない(NBMA への経路は WAN 向きの static/既定経路に限る)**。旧来 3 行構文の `ip nhrp map multicast` の引数は **［③］ハブの NBMA アドレス** で、トンネル IP を書くとユニキャストは全部正常なのに EIGRP だけ retry limit でフラップする(実測)。同じ tunnel source を持つ複数の Tunnel に同じ IPsec プロファイルを貼るときは tunnel protection … shared(全 Tunnel に) が要り、片方だけに付けると設定が拒否される(実測)。稼働中の Tunnel で tunnel protection を変更すると Tunnel が自動的に shutdown されるので、作業手順に no shutdown を入れておく(実測)。underlay と overlay の経路表を分けたいときは **［④］front-door VRF(tunnel vrf <名>)** で tunnel source 側の IF と default route を別 VRF に置く。

### 各空欄の要点

- ① = **D. %TUN-5-RECURDOWN** — p2p GRE 専用のメッセージ
- ② = **B. underlay の経路をオーバーレイの IGP に入れない(NBMA への経路は WAN 向きの static/既定経路に限る)** — NBMA への経路は必ず物理側
- ③ = **A. ハブの NBMA アドレス** — map multicast <NBMA>(実測: トンネル IP だと EIGRP だけフラップ)
- ④ = **H. front-door VRF(tunnel vrf <名>)** — underlay を fVRF に隔離すると再帰ルーティングも構造的に防げる
