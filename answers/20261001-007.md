## 解説

### 完成文: DHCPv6 guard の検査対象とポリシー

(この盤面の世界: **GW ポートは server だが不正端末のポートにポリシーが無い** — 同じ kind でも世界が違えば正解が変わる)

```
ipv6 dhcp guard policy CLIENTS
 device-role client
ipv6 dhcp guard policy SERVERS
 device-role server
 match server access-list DHCP-SRV
!
ipv6 access-list DHCP-SRV
 permit ipv6 host 2001:DB8::53 any
!
interface GigabitEthernet0/1
 ipv6 dhcp guard attach-policy SERVERS
interface GigabitEthernet0/2
 ipv6 dhcp guard attach-policy CLIENTS
interface GigabitEthernet0/4
 ! (ポリシーなし)
```

上はアクセススイッチの設定で、GigabitEthernet0/1 の先に正規の DHCPv6 サーバ(リレー)、GigabitEthernet0/2 に端末、GigabitEthernet0/4 に偽サーバを動かす不正端末がつながる。DHCPv6 guard が破棄するのは、サーバやリレーがクライアント向きに送る **［①］ADVERTISE と REPLY** で、端末が送る SOLICIT/REQUEST は検査せず通す。この盤面で、正規サーバの応答が GigabitEthernet0/1 から入ると server ポリシーなので検査を通って転送される。偽サーバの応答が GigabitEthernet0/4 から入るとポリシーが無いので素通りする。その結果、端末 GigabitEthernet0/2 は先に応答した方の DNS を掴み、偽サーバの値になることがある。`show device-tracking counters interface GigabitEthernet0/1` の Dropped 欄には何も出ない。是正として妥当なのは **［②］GigabitEthernet0/4 に device-role client のポリシーを付ける**。なお **［③］match server access-list** でサーバ/リレーの送信元アドレスも検査でき、優先度は **［④］preference min/max** で範囲を絞れる。

### 各空欄の要点

- ① = **B. ADVERTISE と REPLY** — サーバ発の応答が対象
- ② = **F. GigabitEthernet0/4 に device-role client のポリシーを付ける** — 端末側の全ポートに client を付ける
- ③ = **C. match server access-list** — サーバアドレスの検査は match server access-list。match ra prefix-list は RA guard
- ④ = **G. preference min/max** — DHCPv6 の優先度は preference。router-preference は RA guard

### 語群の残り(どの空欄にも入らない)

- H. SOLICIT と REQUEST — サーバ発の応答が対象
- D. 是正不要(意図どおり) — 端末側の全ポートに client を付ける
- E. match ipv6 access-list — サーバアドレスの検査は match server access-list。match ra prefix-list は RA guard
- A. router-preference maximum — DHCPv6 の優先度は preference。router-preference は RA guard
