## 解説

### 完成文: サーバの死活判定(dead-criteria と deadtime)と show aaa servers

```
RT01# show aaa servers
RADIUS: id 1, priority 1, host 10.99.1.2, auth-port 1812, acct-port 1813, hostname RAD1
     State: current DEAD, duration 312s, previous duration 0s
     Dead: total time 0s, count 0
RADIUS: id 2, priority 2, host 10.99.2.2, auth-port 1645, acct-port 1646, hostname RAD2
     State: current UP, duration 4021s, previous duration 0s

radius-server dead-criteria time 3 tries 1
aaa group server radius RADGRP
 deadtime 5
```

サーバグループの 1 台目が落ちたとき、装置が毎回そのサーバでタイムアウトを待たされないようにするのが死活判定である。**［①］radius-server dead-criteria time/tries** は「何秒応答が無く、何回失敗したら DEAD とみなすか」の条件で、deadtime は DEAD とみなしたサーバを何分間スキップするかである。この 2 つは片方だけでは機能せず、判定条件が無いと **［②］何回失敗しても UP のままで、スキップの出番が来ない**(実測)。上の出力で RAD1 の State が DEAD なので、以後 5 分間は RAD2 に直接問い合わせるので、ログインの待ち時間は 12 秒から **［③］6 秒程度(2 台目分だけ)** に縮む。RAD2 のポート 1645/1646 のように非標準ポートは許され、サーバ側と一致していれば動く。一致していなければ要求は届かず、そのサーバだけが DEAD になる。なお State が UP でも認証できないことはある(鍵不一致など)。DEAD は「**［④］応答が無かった**」であって「認証が通らない」ではない。

### 各空欄の要点

- ① = **E. radius-server dead-criteria time/tries** — DEAD 判定条件
- ② = **D. 何回失敗しても UP のままで、スキップの出番が来ない** — 実測: dead-criteria 無しでは UP 固着
- ③ = **G. 6 秒程度(2 台目分だけ)** — 1 台分のタイムアウト(3×2)だけ残る(実測 6.1s)
- ④ = **H. 応答が無かった** — DEAD は到達性の判定

- F. 全サーバが DEAD になる — 実測: dead-criteria 無しでは UP 固着
