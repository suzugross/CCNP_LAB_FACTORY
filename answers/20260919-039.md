## 解説

### 完成文: PE の MP-BGP 設定と各アドレスファミリが担う範囲

```
vrf definition TENANT1
 rd 65500:200
 address-family ipv4
  route-target export 65500:20
  route-target import 65500:20
!
interface Ethernet0/2
 vrf forwarding TENANT1
 ip address 192.168.1.1 255.255.255.252
!
router bgp 65500
 neighbor 172.31.255.2 remote-as 65500
 neighbor 172.31.255.2 update-source Loopback0
 !
 address-family ［①］vpnv4
  neighbor 172.31.255.2 ［②］activate
  neighbor 172.31.255.2 send-community extended
 !
 address-family ipv4 vrf TENANT1
  neighbor 192.168.1.2 remote-as 65010
  neighbor 192.168.1.2 ［②］activate
  neighbor 192.168.1.2 ［③］as-override
```

上は PE1 の設定である。`address-family **［①］vpnv4**` 配下のネイバー 172.31.255.2 はプロバイダ網内(PE-PE の iBGP) に属する対向 PE で、この AF で VRF TENANT1 の経路が RD 65500:200 付きの VPNv4 経路と VPN ラベルとして交換される。RT は BGP の拡張コミュニティなので、この AF で `send-community extended` が無いと RT が伝わらず、対向 PE はどの VRF にも取り込めない。ネイバーアドレスに Loopback0 の /32 アドレスを使うのは、その /32 に対して LDP が配るラベルがそのまま VPN パケットのトランスポートラベルになるからである。`address-family ipv4 vrf TENANT1` 配下のネイバー 192.168.1.2 は **［④］顧客側(PE-CE の eBGP)** に属し、ここで学んだ経路は VRF TENANT1 の経路表にだけ入る。両拠点の CE が同じ AS 65010 を使うため、PE から CE へ広告する際に **［③］as-override** で AS_PATH 中の 65010 を 65500 に書き換えないと、受け取った CE が自 AS を見つけてループ検出で捨ててしまう。

### 各空欄の要点

- ① = **G. vpnv4** — PE-PE で VPNv4 経路を交換する AF は vpnv4
- ② = **A. activate** — AF でネイバーを有効化するのは activate。next-hop-self は iBGP の次ホップ書き換え
- ③ = **F. as-override** — PE 側で CE の AS を自 AS に書き換えるのが as-override。allowas-in は受信側(CE)で許容する設定
- ④ = **B. 顧客側(PE-CE の eBGP)** — ipv4 vrf 配下は CE との eBGP

### 語群の残り(どの空欄にも入らない)

- D. ipv4 unicast — PE-PE で VPNv4 経路を交換する AF は vpnv4
- H. route-reflector-client — AF でネイバーを有効化するのは activate。next-hop-self は iBGP の次ホップ書き換え
- C. remove-private-as — PE 側で CE の AS を自 AS に書き換えるのが as-override。allowas-in は受信側(CE)で許容する設定
- E. P ルータとの間 — ipv4 vrf 配下は CE との eBGP
