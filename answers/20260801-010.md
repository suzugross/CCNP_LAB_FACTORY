## 注入した故障

- 種別: `filter` — redistribute に route-map が付き特定 Loopback だけ deny(部分喪失)
- 対象: RT04 の router ospf 53 への注入方向(EIGRP AS 301 出自)
- フィルタ被害者: RT01 (98.98.98.98/32)
- 赤ニシン: RT03・RT04・RT06 に未適用の route-map/prefix-list/ACL と無害な適用行(passive-interface Lo0 等)を混入(実害なし)
- 生成: `gen_paper_mcq.py --seed 41007`(sub-seed 7639399 / 展開パック PAPER-RD-7639399・撤収済)

## 各選択肢の判定

- **A**: PL-SVC は RM-SVC の deny 節の match に使われている(seq 5 permit 98.98.98.98/32 のみ)。permit-all を足すと全経路が deny 10 に一致し、全面遮断へ悪化する(被害の拡大)。
- **B**: 隣接関係は確立しており内部経路も学習済み。passive は本事象と無関係。
- **C**: 設定上の欠陥が原因であり、再計算しても状態は変わらない。
- **D**: フィルタの適用範囲を広げるだけで到達性は悪化しうる。要件3(フィルタ適用の禁止)にも真っ向から反する。
- **E**: (正解)
- **F**: 到達性は回復する(症状は改善する)が、再配送へのフィルタ適用が残る。要件3(フィルタ適用の禁止)を満たさない。

## 検証コマンドと期待される出力

- `show ip protocols`(RT04): 対象プロセスの Redistributing 節に出自プロトコルが
  正しい ID・(EIGRP なら) metric 付きで載ること。
- `show ip route`(症状側 RT07): 対岸 Loopback 群が `O E2` として
  現れること。是正前は当該経路が不在(対比側 RT03 には最初からある)。
- 是正後に反映が遅い場合は境界ルータで `clear ip route *`。
