## 解説

### 完成文: DHCPv6 guard の検査対象とポリシー

(この盤面の世界: **GW ポートに端末用(client)ポリシーを付けてしまった** — 同じ kind でも世界が違えば正解が変わる)

```
ipv6 dhcp guard policy DH-EDGE
 device-role client
ipv6 dhcp guard policy DHG-SERVER
 device-role server
 match server access-list DHCP-SRV
!
ipv6 access-list DHCP-SRV
 permit ipv6 host FE80::2 any
!
interface GigabitEthernet1/0/1
 ipv6 dhcp guard attach-policy DH-EDGE
interface GigabitEthernet1/0/10
 ipv6 dhcp guard attach-policy DH-EDGE
interface GigabitEthernet1/0/12
 ipv6 dhcp guard attach-policy DH-EDGE
```

上はアクセススイッチの設定で、GigabitEthernet1/0/1 の先に正規の DHCPv6 サーバ(リレー)、GigabitEthernet1/0/10 に端末、GigabitEthernet1/0/12 に偽サーバを動かす不正端末がつながる。DHCPv6 guard が破棄するのは、サーバやリレーがクライアント向きに送る ADVERTISE と REPLY で、端末が送る SOLICIT/REQUEST は検査せず通す。この盤面で、正規サーバの応答が GigabitEthernet1/0/1 から入ると **［①］GW ポートに付いた client ポリシーで破棄される**。偽サーバの応答が GigabitEthernet1/0/12 から入ると **［②］端末ポートの client ポリシーで破棄される**。その結果、端末 GigabitEthernet1/0/10 は RA は正常だが DNS やドメイン名を取得できない。`show device-tracking counters interface GigabitEthernet1/0/1` の Dropped 欄には **［③］device-role mismatch を含む理由が出る**。是正として妥当なのは **［④］GigabitEthernet1/0/1 のポリシーを device-role server(または trusted-port)にする**。なお match server access-list でサーバ/リレーの送信元アドレスも検査でき、優先度は preference min/max で範囲を絞れる。

### 各空欄の要点

- ① = **B. GW ポートに付いた client ポリシーで破棄される** — client 役のポートでは応答は捨てられる
- ② = **G. 端末ポートの client ポリシーで破棄される** — client 役のポートからの応答は捨てる
- ③ = **A. device-role mismatch を含む理由が出る** — DHCPv6 guard の理由文字列(実測)
- ④ = **F. GigabitEthernet1/0/1 のポリシーを device-role server(または trusted-port)にする** — GW/リレー側は server

### 語群の残り(どの空欄にも入らない)

- H. server ポリシーなので検査を通って転送される — client 役のポートでは応答は捨てられる
- D. match server access-list で破棄される — client 役のポートからの応答は捨てる
- E. Message unauthorized on port が出る — DHCPv6 guard の理由文字列(実測)
- C. 是正不要(意図どおり) — GW/リレー側は server
