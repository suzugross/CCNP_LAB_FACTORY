## 設問

次の説明文(設定例を含む)の空欄 ①〜⑤ に入る語句を、下の語群 A〜J から 1 つずつ選択してください。同じ語句を 2 つの空欄に使うことはありません。語群にはどの空欄にも当てはまらない語句が含まれます。

```
crypto ikev2 proposal PROP-NGE
 encryption aes-gcm-256
 prf sha384
 group 19
crypto ikev2 policy POL-NGE
 proposal PROP-NGE
crypto ikev2 keyring KR-DMVPN
 peer ANY
  address ［①］
  pre-shared-key Wan#Key2026
crypto ikev2 profile IKEV2-DMVPN
 match identity remote address 0.0.0.0
 authentication remote pre-share
 authentication local pre-share
 keyring local KR-DMVPN
 dpd 30 5 on-demand
crypto ipsec transform-set TS-GCM esp-gcm 256
 mode transport
crypto ipsec profile IPSEC-PROF
 set transform-set TS-GCM
 set pfs group19
 ［②］ IKEV2-DMVPN
!
interface Tunnel0
 tunnel protection ipsec profile IPSEC-PROF
```

オブジェクトは［③］の順に参照される。keyring と profile をスポーク間直接通信の相手 NBMA が事前に分からないため wildcard にしている。ピアごとにアドレスを絞ると［④］ので、症状が hub-spoke 間に出ず気づきにくい(実測)。transform-set を transport にするのは GRE で外側 IP ヘッダが既に付いており、tunnel モードの外側 IP 20 バイトが無駄になるからで、両端で食い違っても不通にはならず Tunnel モードに合意して上がる(実測)。［②］を書き忘れると［⑤］。dpd は相手の死活監視(Dead Peer Detection) で、IPsec で保護したトンネルでは GRE キープアライブの代わりになる。crypto map と違い、この方式ではどのトラフィックを暗号化するかの ACL が要らず、Tunnel を通る全パケットが対象になる。

## 選択肢

A. hub-spoke は正常でスポーク間の直接通信だけ成立せず、通信自体はハブ折返しで通り続ける

B. ipsec profile → ikev2 profile → keyring → proposal

C. 10.0.14.1 255.255.255.255

D. hub-spoke の IKE も成立しなくなる

E. 既定の IKEv2 プロファイルが自動で使われる

F. set ikev2-profile

G. 0.0.0.0 0.0.0.0

H. IKEv1(ISAKMP)にフォールバックし、ポリシーが無いので SA が上がらない

I. set peer

J. proposal → policy → keyring → ikev2 profile → ipsec profile → tunnel protection
