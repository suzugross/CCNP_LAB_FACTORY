# XR Track 14 — Data-Plane Protection and QoS

このラボは、XR トラックの単元 **M12 データプレーンの保護と QoS** の実践編です。単元のページは「マーキングと MPLS の QoS の
モデル」(課題 M12-1)、「ポリシングとシェーピング」(課題 M12-2、M12-3)、「データプレーンの保護」(課題 M12-4、M12-5)の
3 つです。各ページを読んでから、ここで課題に順番に取り組みます。各課題は前の課題の上に積み上げます。

## 進め方の約束

- 設定するのは **XR01** と、課題 M12-5 では **RR1** もです。他のルータはすべて据え付けで、変更しないでください。
  確認のためにログインするのは構いません。CE1、CE2、CUST1、CUST2、INET は、顧客とインターネットのものです。
- 課題の中にはコマンド例を示しません。各課題は必要な動作を記述しています。読み物の各ページには設定例がありますが、
  課題の答えと同じ形のものは折りたたんであります。先に自分で解くなら、CLI のヘルプ(`?`)、`show` コマンド、
  Cisco IOS XR のコンフィギュレーション ガイドとコマンド リファレンスを使って、コマンドを見つけてください。
- **Tasks** タブには課題ごとに **Check** ボタンがあります。デバイスの現在の状態を読み取ります。
  押す前にコンフィギュレーション モードを抜けてください。確認は試験のトラフィックを流して数えるので、1 回に 1〜3 分かかります。
- ヒントは 1 段ずつ開きます(キーワード → 参照先 → コマンド)。開いたヒントは記録されます。
- XR01 は **IOS XRv 9000** 26.1.1 で動作しています。XR01 の QoS ポリシーのカウンタは、数十秒遅れて反映されます。
  RR1 は **IOS XRd** 26.1.1(IOS XR のコンテナ版)で動作しています。RR1 はルート リフレクタで、転送パスの外にあります。
- CE1、CE2 の入力と、P1 の XR01 側の入力には、受け取ったパケットを DSCP または EXP ごとに数えるだけの QoS ポリシーが
  据え付けてあります(CE1・CE2 の `COUNT-DSCP`、P1 の `COUNT-EXP`)。確認がこれを使うので、変更しないでください。

## M12 — データプレーンの保護と QoS

### 課題 M12-1

顧客 A との契約では、EF を付けてよいのは音声網(10.46.0.0/16)宛ての通信だけです。サイト 1 の PC は、LAN 宛ての通信にも
EF を付けてしまいます。

- XR01 がサイト 1 から受け取る EF のうち、音声網宛てでないものは、DSCP 0 にして運んでください。それ以外の DSCP は
  変えないでください。
- コアでは、音声網宛ての EF を EXP 5、AF21 を EXP 3、それ以外を EXP 0 で運んでください。積むラベルは、どれも同じ EXP に
  します。

### 課題 M12-2

顧客 A の契約では、業務の通信(AF21)は、契約速度が 256 kbps、最大が 512 kbps です。

- XR01 がサイト 1 から受け取る業務の通信のうち、契約速度に収まる分はそのまま運び、契約速度を超えて最大に収まる分は
  AF22 にして運び、最大を超える分は捨ててください。
- 音声の通信は、この制限の影響を受けてはなりません。課題 M12-1 の動作は保ってください。

### 課題 M12-3

コアの P1 は、混雑への備えとして、PE2 から受け取った業務の通信(EXP 3)を EXP 1 に格下げしています(据え付け)。
顧客 A は、サイト 1 で、コアでの扱いを DSCP で知りたいと考えています。

- XR01 がサイト 1 へ送る通信の DSCP を、コアから届いた EXP に合わせてください。EXP 5 は EF、3 は AF21、1 は AF11、0 は
  DSCP 0 です。
- サイト 1 への出口は、契約の 2 Mbps に整形してください。音声(EXP 5 で届いたもの)は優先して送り、その上限は 512 kbps と
  します。
- P1 と PE2 は変更しないでください。

### 課題 M12-4

- CUST1 は、XR01 に 1 本だけで接続しています。XR01 は、CUST1 から受け取るパケットのうち、送信元が、CUST1 から届くはずの
  アドレスでないものを捨ててください。
- XR01 は、INET から受け取るパケットのうち、送信元がどこにもルートの無いアドレスであるものを捨ててください。既定ルートは、
  ルートがあるものとして数えません。マルチホームの顧客の通信はインターネット経由で戻ってくることがあるので、送信元への
  ルートがどのインターフェイスを向いているかは問いません。
- INET から、プロバイダーのループバック(10.255.0.0/24)とコアのリンク(10.0.0.0/16)へのパケットを、XR01 の入口で
  捨ててください。INET との BGP と、顧客へ向かう通信は保ちます。どの条件に一致したパケットが何個あったかを、条件ごとに
  ハードウェアで数えてください。

### 課題 M12-5

前任者が RR1 に、RTBH の起点を作りました。RR1 でスタティック ルートにタグ 666 を付けると、そのルートが PE に配られ、
PE はそのアドレスへのパケットを捨てます。顧客 CUST2 の 198.51.100.130 が攻撃を受け、宛先の 198.51.100.130 と、攻撃元の
203.0.113.66 が RR1 に登録されています。ところが、攻撃元からのパケットは、今も CUST2 に届いています。

- 攻撃元(RR1 にタグ 666 で登録したアドレス)から来るパケットを、XR01 の入口で捨ててください。攻撃を受けている宛先への
  パケットも、引き続き XR01 で捨てます。
- RR1 に登録したアドレスのルートを、インターネットへ広告してはなりません。
- 起点の仕組みはそのまま使います。攻撃元や宛先の足し外しは RR1 だけで済み、XR01 に個々のアドレスを書いてはなりません。
- PE2 は変更しません。PE2 は従来どおり、登録された宛先へのパケットを、捨て先の 192.0.2.1 を経由して捨て続けます。
