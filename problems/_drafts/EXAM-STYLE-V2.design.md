# 試験文体層 v2 — 「条件形・単元不明・長い一文」＋見た目の再現（BL-207）

起票 2026-09-21。発端= ユーザの ENARSI 受験所感（2 回目）。
既存の Cisco 語規約（訳語の揺れ・直訳構文）と BL-088 不親切化（括弧除去・設問統一・散文化）の上に載せる層。

## 1. 観察（ユーザ所感・言い回しの型のみ記録）

- 設問文・要件文は**必要最小限でおおざっぱ**。ただし完全再現は不要（本試験は正当性に欠ける箇所もある）。
  → 方針= **正当性（正解の一意性）を担保したまま**、おおざっぱ・不親切・意図がわかりにくい方向へ寄せる。
- **目的が「条件」の形で書かれる**: 「〜から〜へすべての通信が行われるという条件において、必要な設定を下記項目から選択しなさい」。
- **単元名を言わず対象物だけで話す／複数単元が 1 文に混ざる**: 「〜のステートメントを設定し、eigrp で static ルートを再配布する」型。
- **一文が長い**（条件・制約を 1 文に詰める）。
- 選択肢は **config 断片**（route-map / access-list 等）。
- **図はアドレス等が充実している → 図は削らない**（2026-09-21 ユーザ訂正）。
- config / log の塊が**無作為に配置**されている。
- **CCNP の用語ではないが IT 一般で使う語**が出る（例: 「NMS サーバからの通信の応答が〜」）。（2026-09-21 追記）
- **「どちらも動くが片方だけ正しい」ひっかけが多い**（2026-09-21 追記）。例= 送信元をプレフィックスで止める deny seq20 に対し、(a) seq15 に対象通信だけの permit を挿入 ／ (b) seq20 を削除し seq5 に同じ permit。対象通信はどちらでも通る。要件に「既存行を温存」の明記は無かった。
- config / log は画像で、**行間がわずかに広く、ぼやっとして次の行を目が拾いにくい**。

### ★方針転換（2026-09-21 ユーザ指摘）= 「量で読みにくく」→「構文で読みにくく」

本 PJ の従来の不親切化（BL-088・Cisco 語規約の一部）は**文章量を増やして**読みにくくしていた
（前置きの水増し・要件の重複・シナリオ散文化）。本試験はその上を行き、
**必要なことしか書いていない（情報は最小）のに、構文が読みにくく、一文が長く、要点がつかめない**。

- 目標= **情報量は最小・構文の負荷は最大**。水増し（担当者設定・作業時間帯の理由・同じ要件の言い換え）は**やめる**。
- 読みにくさの担い手を構文へ移す: 条件句化（R1）・機構名の除去（R3）・1 文への統合（R4）・長い連体修飾・
  直訳の係り受け（「〜であるところの」「〜という条件において」）・主語/目的語の省略・IT 一般語（R8）。
- 1 文に要件・制約・設問を詰めてよいが、**要件の要素は各 1 回だけ**出す（重複で冗長にしない）。
- BL-088 の「次の候補= 無関係な前置きの水増し」は**採らない**。

## 2. 変換規則（生成済み Markdown への後処理＝`obfuscate_md` 拡張）

| # | 規則 | 備考 |
|---|---|---|
| R1 | 要件（「〜できること」「〜してはならない」）を **「〜が…されるという条件において」** の条件句へ畳む | 到達要件＋隔離要件は「〜**のみ**が…される」で 1 句にできる |
| R2 | シナリオの前置き（担当者設定・作業時間帯の理由付け・「一部の通信が意図どおりでない」）と要件の言い換え重複を削除（水増し廃止） | 故障の存在は出力から気付かせる |
| R3 | 要件・設問から**機構名（PBR/再配送/CoPP 等）を除去**し対象物（プレフィックス・ステートメント・プロセス）で言う | 制約（「PBR の適用ポイントを変えない」）に残る機構名は許容＝本試験も制約には出る |
| R4 | 条件＋「必要な設定を下記の項目から選択しなさい」を **1 文に統合**し、制約を 1〜2 文で後置 | 長い一文が主目的 |
| R5 | 設問形と選択肢の種類を一致させる（config 断片なら「必要な設定を選択」） | 現行は「理由を判断」なのに選択肢が config の食い違いあり＝これは欠陥修正 |
| R6 | 出力ブロックの順序シャッフルを **常時**（BL-088 は 50%）・ブロック見出しなし | |
| R7 | 図・リンク一覧は**削らない**（アドレス充実のまま） | |
| R8 | 盤面の役割を **IT 一般語**で呼ぶ（NMS サーバ／監視サーバ／運用端末／踏み台／業務システム／基幹系／拠点 PC 等）。「通信の応答」のように**向きを曖昧にした言い方**も混ぜる | 語は盤面のノードに一意に対応すること（図のラベル・ACL/SNMP/logging の宛先から特定可）。語と役割の対応表は生成器側に持ち、seed で語を揺らす。「応答」の向きの曖昧さは、盤面から一意に補完できる場合に限る（未提示と未決定の区別＝既存規約） |

### 正当性ガード（必須）

- 削った文の情報が、盤面（図・出力・config）か条件句に残ること＝BL-088 の「情報は 1 ビットも減らさない」を継承。
- **誤答肢が条件句だけで落ちること**を選択肢ごとに確認（selftest 化: 各誤答肢に「違反する条件句」を 1 つ対応付ける）。
- ★**暗黙の最小変更原則**（2026-09-21 制定）: 要件に明記がなくても「**要件に無い通信・経路・挙動の扱いを変えない**」を前提とし、それに反する肢は誤答とする。R1 で制約文を条件句へ畳むとき、この原則で担保できる制約（「対象以外に影響しない」系）は**文面から落としてよい**。担保できない制約（行数・手段の縛り等）は残す。
  - selftest: 各選択肢の適用後状態を、対象トラフィック以外のプローブ集合でも評価し、**正解肢だけが「対象外の挙動が不変」**であることを検査する（acl_model.py で評価可能）。
  - 正解は**差分が最小**で、かつ対象外が不変の肢。「消すだけで足りる」盤面で permit 追加を含む肢は冗長として作らない（不自然な正解を避ける）。
- 条件形にすると到達性の前提（例: コアが経路を持たない）が不要になる場合がある → 前提を削るのはその場合に限る。

## 3b. ひっかけの型（「どちらも動く」2択）

本試験は「対象の要件はどちらでも満たせるが、副作用で片方が落ちる」肢の組が多い。正解の根拠を**明記しない暗黙原則**に置く（上記の最小変更原則）。型の候補:

| 型 | 正解 | 紛らわしい肢（要件は満たすが副作用あり） |
|---|---|---|
| ACL 挿入 vs 削除 | 広い deny の手前に狭い permit を挿入 | 広い deny を削除＋permit（同サブネットの他ホストまで開く） |
| ACL 行の位置 | 既存の deny より前の seq | 末尾に permit を追加（暗黙 deny の前でも、先行 deny に食われて効かない＝これは要件未達側） |
| route-map の追記 | 既存 seq の前に permit seq を挿入 | 末尾の `permit` 無条件を広げる／既存 deny seq を削除 |
| distribute-list / prefix-list | 対象プレフィックスだけ除外 | `le 32` を付けて範囲ごと除外 |
| 再配送の範囲 | route-map で対象のみ | 再配送自体を外して static で代替（他経路の到達性が変わる） |

各型で「要件だけ読むと両方正しく見える」ことが目的なので、**要件文には副作用の禁止を書かない**（書くと型が消える）。
★**副作用が及ぶ相手（同サブネットの別ホスト等）も盤面に出さない**（2026-09-21 ユーザ訂正= 本試験にはいなかった）。
根拠は構成の行が及ぶ範囲そのもの（/24 の deny を消せば /24 全体が開く）で、構成から一意に読めるので「未決定」にはならない。
範囲の読み取りに必要な行（ACL 本体・適用点・ワイルドカード）は提示する。
