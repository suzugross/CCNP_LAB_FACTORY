## IOS側の要件

1. **サーバ登録**: `radius server` 定義 ×2（名前付き new-style 必須）
2. **ポート設定**: SRV02 は auth-port/acct-port を仕様書に合わせる
3. **共有キー**: サーバ毎に異なる key
4. **サーバグループ**: `aaa group server radius <GRP名>` に2台登録＋`deadtime`
5. **ローカルDB**: 緊急用ローカル管理者（例 `emg-admin` priv15）＋SUZUKI維持。方式リストは `group <GRP> local`
6. **ひねり①（送信元）**: サーバは Lo0 からのみ受理 → `ip radius source-interface Loopback0` に自力で気付かせる（外すとサイレント無視→タイムアウトの実戦的症状）
7. **ひねり②（タイマ）**: 「片系障害時のログイン遅延を数秒以内に」→ `timeout`/`retransmit` チューニング（採点高速化も兼ねる）
8. （採否未決）`aaa accounting exec default start-stop group <GRP>` — サーバ側ログで採点

RADIUSアカウント台帳（admin=priv15 / monitor=priv1 / **SUZUKI登録必須**）は既存問踏襲。
「Reject時はlocalへ落ちない」締め出し教訓も維持。

## 採点設計（目玉: 3フェーズ挙動採点）

1. **正常時**: 両RTで `test aaa group <GRP> … legacy` Accept、SSH実ログインで priv-lvl、誤パス Reject
2. **SRV01停止**（採点PBが SSH で `systemctl stop freeradius`）: それでも Accept → SRV02のポート/キー/グループ登録の証明
3. **両サーバ停止**: ローカル `emg-admin` でSSHログイン成功 → ローカルフォールバックの証明 → **always 節で必ず両サーバ再起動**

構成検査（show run regex）は方式リスト順序・グループ所属など挙動で見えない部分のみ。
`show aaa servers` の "auth-port 1912"（コロン無し表記）実効値も採点。

## 実機検証（seed 51201）

- 基線（AAA 未設定）= **6/100**
- 模範解答投入 = **100/100**、そのまま**連続 4 回**採点しても 100/100（破壊フェーズの自己復旧を確認）
- 負のテスト①: RT02 の `dead-criteria` を外す → **94**（挙動③のみ FAIL）
- 負のテスト②: RT02 に `username <RADIUS管理者>` を作る → **94**（挙動⑤のみ FAIL）

## 実装で踏んだ罠

1. **基線で 6 点入った**。挙動②（遅延 ≤ 5 秒）は、ログインが失敗すれば当然速いので
   無設定でも通ってしまった → `PHASE2=OK` と抱き合わせた。
2. **挙動④が無設定でも通った**。ローカル管理者は AAA が無くても入れる。
   → 「サーバを試した末に落ちた」ことを**待ち時間**（>1.5 秒）で裏取りする。
3. **2 回目の採点で挙動③が落ちた**。前回の破壊フェーズで優先サーバが DEAD 記録のままだと、
   止めても最初から速い → 冒頭で `show aaa servers` を見て**優先サーバの UP を待つ**。
4. **優先サーバの順序に依存する**。SRV02 を先に置かれると挙動③が観測できない
   → 要件 2 に「**SRV01 を優先**」を明記し、`PRIMARY` トークンで取り違えを可視化した。

# ★初出題(2026-08-10・GEN-AAAGRP-88406)で判明した罠と方針

## 罠: `aaa group server radius` 内の `timeout` / `retransmit` は効かない

実測と文献調査の全文は [poc/aaa/README.md](../../poc/aaa/README.md) §19.8。要点:

- グループ内に書くと**受理されるが名前付きサーバの実効値にならない**。値は
  **per-server → global** の順で解決され、グループの記述はその探索に入らない。
- 症状は「片系断でログインが数十分返らない」。`debug radius authentication` に
  `Started 2000 sec timeout` が出たきり、**再送も failover も `%RADIUS-4-RADIUS_DEAD` も出ない**。
- グローバルへ移し `radius-server dead-criteria` を足すと正常化する。

**要件文は置き場所を縛っていない**ので、受験者の書き方でも要件を満たしているように読める。
それでいて結果が「減点」ではなく「機器に入れなくなる」。模範解答が最初からグローバル側に
書いていたため、実装時の検証はこの罠を素通りしていた。

## 方針: 罠は残す(ユーザ決定 2026-08-10)

選択肢は A=要件文で置き場所を縛る / B=罠を残して採点で検出 / C=B＋コンソールを AAA から外す。
**ユーザは B を選択**。理由=「普段コンソールから触る。締め出しでもリブートで戻る」。

この判断は実挙動とも整合する。**締め出しは片系断のときだけ**現れ、両サーバ生存時のログインは
正常なので、リロードすれば必ず復帰する(恒久的な文鎮化は起きない)。

実装= 各ルータに**0 点の診断チェック**を追加。
`show running-config | section aaa group server radius` にタイマ行が無いことを見る
(点は動かさない。減点は挙動①②③が既に行う)。落ちた理由が**名前で分かる**ことが目的。

## 同時に直した採点系の不具合(すべて初出題で露見)

| # | 不具合 | 対処 |
|---|---|---|
| 1 | プローブの ssh がハングし採点全体が止まる | 全 ssh に `timeout` を付与 |
| 2 | ★**IOL は強制終了された SSH の VTY を解放しない**(§19.6)。採点 1 回で 4 本焼き、以後 SSH 不能 | `ServerAliveInterval`/`CountMax` で**ssh 自身に切断させる**。`timeout` は最後の安全網 |
| 3 | 挙動②③がログイン失敗のせいで PASS する偽陽性(§19.7) | `PHASE2=OK` と抱き合わせ |
| 4 | 挙動④が AAA 未設定でも PASS | 待ち時間(>1.5s)でフォールバックを裏取り |
| 5 | 前試行の DEAD 記録で挙動③が壊れる | フェーズ冒頭で優先サーバの UP を待つ |
