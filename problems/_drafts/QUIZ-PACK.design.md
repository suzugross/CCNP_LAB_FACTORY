# 問題パック（連続出題）設計メモ — BL-099

2026-08-08 ユーザ発案。「1問一答」から「5問セットの連続出題」へ。
紙面3問＋ラボ2問を1パックにまとめ、問題文を HTML でユーザフォルダへ出力し、
ユーザは1枚の解答用 Markdown に書き込む。採点はパック単位でまとめて行う。

## 1. 確定した方針（2026-08-08 ユーザ判断）

| 論点 | 決定 | 理由・影響 |
|------|------|-----------|
| 出力先 | **リポ内 `packs/<PACK-ID>/`** | VSCode の CCNP01 ツリー内で完結（`lab/<ID>/` と同じ思想）。`.gitignore` に `/packs/` を追加して使い捨て |
| 紙面の調達 | **パック作成時に都度生成** | 常に新 seed。1問あたり実機ラボを建てるため所要 10〜15分／3問だが、夜間実行なので非問題 |
| ラボの起動 | **2問同時起動（合計20ノード以内で選定）** | 待ちゼロで好きな順に解ける。選定側で台数合計を検査（下記 §4） |
| 実行タイミング | **★夜間バッチ（就寝前に起動→翌朝完成）** | 所要時間は制約にならない。代わりに「**朝、確実に解ける状態になっている**」ことが最重要要件（§4.5） |

### ★ 夜間バッチであることの帰結

ユーザの運用は「寝る前に Claude にパックを作らせ、翌朝から1日かけて解く」。ここから:

1. **所要時間は最適化対象ではない。** リトライ・検証・待ちを厚くしてよい。むしろ**確実性に全振りする**。
2. **失敗の代償が大きい。** 朝起きて問題が4問しかない／ラボが上がっていない、は1日を潰す。
   → 各フェーズに**自動リトライ**と**完成判定**を入れ、未達なら朝に「何が欠けたか」を明示する。
3. **ラボは一晩＋丸一日、起動したまま。** パック期間中は CML の枠をほぼ占有する
   （他ラボの provision も、紙面の追加生成も走らせない前提）。パック中の追加出題依頼が来たら
   台数を確認してから受ける。
4. **起動直後の処置は夜のうちに済ませておく。** IOSvL2 の Vlan999 SVI bounce、CVAC day0 の
   config 欠損対策（`cvac_bringup.py` / `bringup_console`）などは、ユーザが朝触る時点で
   完了していなければならない。provision 後の bringup を**パック作成の必須工程**にする。

## 4. `pack.sh` のコマンドと処理順

```
pack.sh new    <PACK-ID> [--paper 3] [--lab 2] [--budget 20]
pack.sh status <PACK-ID>
pack.sh grade  <PACK-ID>
pack.sh close  <PACK-ID>
```

### new（★実行順序が制約）

「都度生成 × 同時起動」を選んだので、**紙面を先に全部焼き切ってからラボを建てる**順序が必須。
紙面生成は問題ごとに CML ラボを provision → boot 待ち → 収集 → teardown するため、
ラボ2問が先に建っていると 20ノード上限に当たる。

1. `lab.sh status` で稼働中ラボの台数を取得（`used`）。
2. **紙面フェーズ**: `gen_paper_mcq.py --seed <新> --count 3 ...` を実行（この間に建つラボは自分で撤収する）。
3. **選定フェーズ**: CATALOG から未出題・分野非重複のラボ問題を2問選ぶ。
   制約 = `used + nodes(labA) + nodes(labB) <= budget`（既定 20。安全側に 16 推奨）。
   満たす組合せが無ければ、台数の小さい候補へ落とすか、ユーザに teardown を提案して中断。
4. **構築フェーズ**: 2問を `lab.sh provision`（並列可・所要 3〜7分）。
5. **bringup / 健全化フェーズ**（§4.5）。
6. `render_html.py` で `q1..q5.html` と `index.html` を生成、`解答.md` の雛形を書き出す。
7. `_history.md` にパック1行＋各問1行を `出題中` で追記。

所要は合計 15〜25分（＋検証で延びる）。**`nohup` バックグラウンド実行＋ `topologies/_state/pack-<PACK-ID>.log`**
に全工程を追記し、ユーザは就寝、翌朝 `index.html` を開く。

### 4.4 選定から外すもの（2026-08-08 ユーザ指示）

**純粋な Cisco 問題以外は既定で選定しない。** CCNP の試験対策として想定外の分野が
混ざるのを防ぐ（初回パックで FreeRADIUS 構築 `GEN-RADIUS` を出してしまった反省）。
判定は「設定作業の主対象が Cisco 機かどうか」:

- ID 接頭辞 `FGT-` / `JUNOS` / `CLAB-`（他ベンダ機）
- 生成器ファミリ `GEN-RADIUS`（FreeRADIUS）/ `GEN-DNSDHCP` / `GEN-DNSTS`（BIND9）/
  `GEN-ZBXBUILD`（Zabbix）＝ Linux サーバ構築系
- 分野タグ `junos` / `multivendor` / `bind9` / `dns` / `sdwan` /
  `firewall-policy` / `asa-config-reading`

`--allow-non-cisco` で解除できる。**外部機器が単なる観測機（Zabbix のポーラ等）である
場合は対象外**＝ `GEN-SNMPTS` は設定対象が Cisco ルータなので残す（ユーザ確認済）。

**自動化ラボも除外**（`ANSIBLE-*` / `NETAUTO-*` / `-AUTO-` / タグ `automation` 等）。
対象機は Cisco だが、試験のシムレットで解答を要求されないため（`--allow-automation` で解除）。

**ラボは既定で TS のみ**（`--any-lab` で構築問・ドリルも可）。判定は
生成器なら script 名（`…ts.py` / `troubleshoot`）と説明文（TS/トラブル/故障/ループ/障害）、
静的問題なら ID の `-TS` とタグ `troubleshooting`。

### 選定ロジックで踏んだ罠（2026-08-08・全て実データで発覚）

1. **既存インスタンスが無い生成器が候補から丸ごと落ちる。** 台数を「CATALOG の
   GEN インスタンス一覧の中央値」で見積っていたが、主力 TS 生成器は検証 seed を
   掃除済みでインスタンスが 0 件 → DMVPN・EIGRP×VRF・DHCP・FNF 等が全滅していた。
   → 説明文から台数を読む（`4 IOL` / `3〜8台`）＋既定値 6 のフォールバックに変更。
2. **メタタグが分野重複判定を壊す。** `troubleshooting` / `generated` はタグではあるが
   分野ではない。1問目を選んだ時点でこれが `tags_used` に入り、**他の TS 問題が全て
   弾かれて**選定が1種類に固定されていた。→ `META_TAGS` を判定から除外。
3. **説明文がまるごと1タグ化。** インスタンスが無い生成器はタグが取れず、散文が
   1個のタグになって重複判定を素通りしていた。→ キーワード辞書からタグを起こす。
4. **★（CATALOG の主力印）を強く重み付けすると固定化する。** 候補が少ない時に
   同じ生成器が毎回選ばれた。→ 乱数を主・★は 0.4 倍の弱いタイブレークに。
5. **生成器ファミリの重複回避 90 日は長すぎる。** GEN 系は新 seed で盤面も故障も
   変わるため、90 日封じると候補が枯れる（実測 4 種まで減少）。
   → 同一インスタンスは 90 日、**ファミリは 21 日**（`--family-days`）の2段構えに。

### 4.4.1 ★台数の数え方は「CML の実態」でなければならない（2026-08-08 実機で被弾）

当初は MGMT リース台帳（`topologies/_state/mgmt_leases.json`）から稼働ノード数を
出していたが、**実機と大きくずれる**:

| | 台帳の認識 | CML の実態 |
|---|---|---|
| 稼働ノード | 8 | **27** |

ずれの原因は3つ、いずれも構造的:

1. **リポ外のラボを知らない** — ユーザの手組みラボ（「それぞれ別のプロトコルで学習
   したい」5台）は台帳に載らない。
2. **停止中のラボをカウントしてしまう** — `FGT-LAB` はリースが残るが STOPPED。
3. **リースは管理対象ルータのみ** — CML はブリッジ・外部接続もノードとして数える
   （例: リース6に対し実機8ノード）。

結果、12台の `GEN-MPLSTS` を選定して provision し、CML の
`20 of 20 node licenses are in use` で失敗。**さらに失敗したラボが 14 ノードで
STARTED のまま残り**、放置すればライセンス枯渇で以後すべての provision が落ちる
状態になった（手動で撤収）。

→ `cml_started_nodes()` を追加し、**CML API に問い合わせて STARTED のラボの
ノード数合計**を予算検査に使う。CML 到達不能時のみ台帳へフォールバック。

**対処済**: `provision_lab()` は失敗時に必ず `lab.sh teardown` を打つようにした
（ライセンス上限のメッセージを検出したら理由にも明記する）。

### 4.5 「朝、確実に解ける」ための完成判定（★夜間バッチの中核）

各フェーズは**成功を機械的に確認してから次へ進む**。未達なら自動リトライし、
それでも駄目なら `index.html` の冒頭に**赤字で欠落を明示**する（黙って4問のパックを作らない）。

| フェーズ | 完成判定 | 未達時 |
|---|---|---|
| 紙面生成 | `questions/<stamp>.md` が要求数ぶん存在し、`answers/` に対応キーがある | **別 seed で自動リトライ（最大3回）**。`gen_paper_mcq.py` は展開失敗時に問題数を黙って減らすため、この検査は必須 |
| ラボ選定 | 台数合計 ≤ budget、`_history.md` と重複なし、CATALOG 備考の固有注意を manifest に転記 | 台数の小さい候補へ落とす／候補枯渇なら1問だけで続行し index に明示 |
| ラボ構築 | `lab_up` 成功＋全ノード到達（MGMT ping）＋`lab/<ID>/問題.md` が存在 | provision リトライ1回 → 駄目なら別問題へ差し替え |
| bringup | IOSvL2 は Vlan999 SVI bounce、CVAC 系は `cvac_bringup` 完了、console 専用機はログイン確認 | リトライ。ここを飛ばすと「朝、ping が永遠に上がらない」事故になる |
| **ベースライン採点** | `grade.yml` を1回流し、**得点が想定レンジに入る**ことを確認（TS 系は broken 前提で低得点、構築問は 0 点付近） | 想定外（例: TS なのに満点＝故障が入っていない）なら**その問題を差し替え**。★これが「朝、実は解けない／実は既に解けている」事故の最後の砦 |

ベースライン得点は `manifest.yml` に記録し、`report.html` で「開始時 X 点 → 最終 Y 点」と出す。
なお `_history.md` の得点欄には**最終得点のみ**を書く（従来どおり）。

### 4.5.1 bringup（実装 2026-08-08）

`lab_up.yml` が problem.yml の `bringup_data_ifs` / `bringup_console` で
IF の no shutdown と CVAC 後の bringup を既に面倒を見ている。パック側はその**後段**
＝「実際に到達できるか」を担う:

1. `mgmt_map.yml` の全ノードへ ping（最大8回・15秒間隔）
2. 落ちているノードが **IOSvL2** なら（生成 `lab.yaml` の `node_definition` で判定）
   `fix_console.py` 経由で **Vlan999 の shut/no shut** を打って再確認
3. なお落ちていれば manifest に `warn` を残し、index.html に明示する

※ 2 は IOSvL2 を含むラボが選定されないと実走しないため、**実機未検証**。
   初めて IOSvL2 が選ばれた回で確認すること。

### 4.6 夜間の耐障害

- CML ホスト再起動・ラボ停止に備え、`pack.sh status` が**朝いちで全ラボの稼働を再確認**する
  （落ちていれば `lab start` 相当で復帰を試みる）。
- 一晩の連続稼働で隣接がフラップしていないかは、上記ベースライン採点＋朝の status で検出する。
- ビルドログ(`topologies/_state/pack-<PACK-ID>.log`)は削除しない。朝、何が起きたかを
  Claude が読んで説明できるようにする。

### grade（実装済）

1. `解答.md` をパースして各問の解答・状態を抽出。
2. 紙面 MCQ = `answers/<ref>.md` の正解記号と突合（自動）。
3. 紙面 記述（shape=bgpdbg）= `answers/` のルーブリックを Claude が採点。
4. ラボ = `grade.yml` を実走し、得点と**未充足チェック名**を取得（`--no-lab` で省略）。
5. `report.html` 生成 ＋ `_history.md` を `採点済` に更新。

**report.html の約束**: 未解答の問題については**正解も解説も出さない**
（採点を先に流しても、まだ解ける状態を壊さない）。解説は `answers/` の
「各選択肢の判定」と「教育核心」だけを引く（仕込みの種別・seed は出さない）。

### `_history.md` の自動更新（実装済・★上書き禁止）

`new` で `出題中`、`grade` で `採点済`＋得点、`close` で `撤収済` に更新する。
既存行があれば状態・得点だけを書き換え、**メモ欄は空欄のときしか触らない**。
メモは Claude が採点後レビューで書く学習記録の本体で、自動生成の定型文で潰すと
台帳の価値が失われる（実装中に一度潰して復元した）。

### close

全ラボ teardown → `_history.md` を `撤収済` → `packs/<PACK-ID>/` は残す（report を後で読めるように）か削除かは `--keep` で選択。

## 5. 解答用紙 `解答.md` のフォーマット規約

機械可読にするため見出しを固定する。ユーザは `状態:` と本文だけ触ればよい。

```markdown
# 解答用紙 — PACK-20260808-A

## Q1 (紙面 20260808-004)   状態: [ ] 未着手
解答:
根拠:

## Q4 (ラボ GEN-DMVPN-1234)  状態: [ ] 未着手
メモ:
```

### ブラウザから直接書き込む（2026-08-08 追加）

`scripts/pack.sh serve` は静的配信サーバではなく `topologies/pack_server.py`。
各問のページ下部に解答欄（紙面=実在する選択肢だけのラジオ／記述式=自由記述／
ラボ=メモ＋実装完了チェック）を出し、入力を API 経由で `解答.md` に書き戻す。

  GET  /_api/sheet?pack=<ID>&no=<N>  … 該当セクションを返す（開いた時に復元）
  POST /_api/sheet?pack=<ID>&no=<N>  … 該当セクションだけ差し替える

安全側の約束:
- **127.0.0.1 のみに bind**。pack 名は `PACK-[A-Za-z0-9_.-]+` で検査し、
  解決後のパスが `packs/` 配下に収まることも確認する（`../` は 404）。
- **書けるのは `packs/<ID>/解答.md` だけ**。ファイル全体ではなく
  **該当セクションのみ差し替え**（複数タブ・VSCode 同時編集で他の問を消さない）。
- 保存は一時ファイル＋rename の原子的置換。見出し行が不正な POST は 400。
- サーバ経由でない（`file://`）場合は解答欄に「保存できません」と出し、
  `解答.md` を直接編集する運用にフォールバックする。

`解答.md` の書式は下記のまま。ブラウザで書いても VSCode で書いても同じ結果になる。

- 紙面 MCQ は `解答:` 行に記号1文字。紙面 記述は `解答:` 以下に自由記述。
- ラボは**実機の設定が本体**なので `状態:` を `[x] 実装完了` にするだけでよい（`メモ:` は任意）。
- パーサは見出し行の `Q<n> (種別 <ref>)` と `状態:` のチェックボックスだけを見る（本文の自由度は保つ）。

## 6. HTML レンダラの要件

- markdown-it-py（`.venv` 導入済 4.2.0）＋ Pygments（2.20.0）。CSS はインライン埋め込みの単一ファイル。
- **コードフェンス（show 出力・ASCII トポロジ図）を絶対に崩さない**: 等幅・折り返し無し・横スクロール。
  紙面問題は図と show 出力が主役なので、ここが品質の要。
- **既定は「ふつうの HTML」**（`--mermaid cdn`）。CSS はインライン、mermaid だけ CDN 参照で
  **1ページ 12〜18KB**。ユーザは Windows 側のブラウザから開く（リモート接続元は Windows）。
- **オフライン用に `--mermaid embed`** を用意（`topologies/assets/mermaid.min.js` 3.5MB を
  埋め込み＝外部参照ゼロ・1ページ 3.5MB）。ネットに出られない閲覧環境向けの保険。
  `--mermaid none` は図をソース表示のみ。
- **描画に失敗した場合はページ上に警告を出し、図のソースはそのまま残す**
  （BL-087 の「図はリンク一覧の劣化コピー」原則により、図が出なくても解答可能性は失われない）。
  CDN が届かない環境では警告文が `--mermaid embed` での作り直しを案内する。
- **テーマは試験画面風の白一色**（ユーザ要望）。ダークモードには追随しない
  （`color-scheme: light` 固定）。塗りを使わず罫線だけで区切り、角丸・影・アクセント色なし。
  mermaid も `theme:'neutral'` で白基調に揃える。印刷 CSS も入れる。
- **ハイライトは行わない**。show 出力に色を付けると「どこが要点か」の道標になり、
  BL-088（道標の除去）と逆行するため。
- **選択肢は1つずつ独立したカードにする**。問題文の Markdown は選択肢を改行だけで
  並べており、Markdown の規則で連続行が1段落に畳まれて全部つながって見えるため、
  描画側で空行を補って分ける（`separate_choices()`）。
  ※生成器側も 2026-08-08 に `render_options()` を `"\n\n".join` へ修正済
  （Markdown を直接読む場合の根治。obfuscate_md が空行を保持することを確認済）。

## 6.5 夜間バッチ v2（2026-08-09 ユーザ決定・**フェーズA=実装済／実機はこれから**）

初回パック（紙面3＋ラボ2）の運用を踏まえた次の形。**実装はまだ着手しない**。

### 紙面: 10〜20問（必須ジャンルあり・2026-08-11 更新）

問題数は `--paper auto`（既定）で **10〜20問から毎回抽選**する（「適当にばらつかせる」
というユーザ指示）。`--paper 12` で固定、`--paper 8-14` で範囲指定もできる。

**必須ジャンルは `redist,aaa,acl`**（`--require-shape`）。`acl` は IPv4/IPv6 の
ACL 紙面（`acl` / `aclv6` から抽選）。

**`--paper-only`** で紙面だけのパックにできる（ラボを作らない＝ CML のラボ枠を使わない）。

### 紙面: 必須ジャンルの実現方法

| 枠 | 指定 | 実現方法 |
|---|---|---|
| 再配送 ×1以上 | 必須 | `chain` / `ring` / `mploop` / `leakmap` / `v6redist` から抽選して1回だけ専用生成 |
| AAA ×1以上 | 必須 | `shape=aaa`（BL-101/BL-103 で完成済）で1回だけ専用生成 |
| ACL ×1以上 | 必須 | `acl` / `aclv6` から抽選して1回だけ専用生成（2026-08-11 追加） |
| 残り | 自由 | `--shape mixed` でまとめて生成 |

`--shape mixed` はジャンルを保証しないため、**必須ジャンルは shape 指定で個別に生成し、
残りを mixed で埋める**方式にする。所要は 30〜40分（紙面専用 shape が引かれれば大幅短縮）。

### ラボ: 固定ジャンル2問（＋余裕があれば1問）

固定ジャンルは3つ。**H型は EIGRP版／OSPF版をまとめて1ジャンル**として扱う
（同時に2本入れると盤面がほぼ同じになるため）。

| ジャンル | 生成器 | 台数 | 接続 |
|---|---|---|---|
| **H型 VRF** | `pvt_gen_eigrp_vrf_h.py`（**EIGRP優先**）/ `pvt_gen_ospf_vrf_h.py` | 6 | console |
| **DHCP TS** | `gen_dhcp_ts.py` | 5 | ssh |
| **DMVPN TS** | `gen_dmvpn_ts.py` | 4 | ssh |

- この3ジャンルから**2つ**を選ぶ（組合せ3通り × H型のバリアントで実質5通り）。
- **3問目は「余裕があれば」**＝ CML の実稼働ノード数を見て入るときだけ、通常の
  TS プールからランダムに追加する。入らなければ2問で確定（無理に詰めない）。
- 台数: 最大 H型11台＋その他6台＝17台。手組みラボ（5台）が起動していると
  22台で上限超過 → 3問目は自動で見送られる関係。

### 実装状況（フェーズA・2026-08-09・CML 不使用で検証）

実装済み。既定値も v2 に切り替えた（`--paper 8` / `--require-shape redist,aaa` /
`--lab-genres hvrf,dhcp,dmvpn` / `--lab 2` / `--lab-extra 1` / `--reserve 3`）。

| 固定ジャンル選定 | seed 12通りで3組合せがほぼ均等（H+DMVPN 4 / DHCP+DMVPN 5 / DHCP+H 3） |
| H型 EIGRP 優先 | 全 seed で `PVT-EGVRFH` を選択 |

### 実装時に必要な調整（すべて対応済）

1. **固定ジャンルは重複回避（`--family-days`）の対象外**にする。毎晩指定するため、
   履歴チェックを効かせると2日目以降に候補ゼロで落ちる（新 seed なので実質重複しない）。
2. **固定ジャンル同士は分野タグの重複チェックも外す**（H型と他が `vrf` 等で衝突する）。
3. **PVT 系を候補に入れる**: `private/CATALOG.md` も読む。H型2種はどちらも private 側。
4. **PVT の台帳分離**: `_history.md` の自動更新を、PVT系は `private/_history.md` へ
   振り分ける（CLAUDE.md の規約。公開ファイルに PVT の出自・内容を書かない）。

### 既知のリスク: 固定ジャンルの消化ペース

毎晩同じ生成器を回すため、単発故障のバリエーションは**数週間で一巡**する見込み。

- DMVPN: 16故障中**未出題は u1 / i4 / i7 / i8 の4種**
- DHCP: 8故障中、主要なものは既出

## 6.6 出題資産の更新への追従（2026-08-11 の棚卸し）

他セッションが紙面資産を大きく更新していたため、パック側を追従させた。
**問題の作り手とパックの作り手が別セッションなので、資産の更新はパックの前提を
黙って壊す**。定期的にこの突き合わせが要る。

| 資産側の更新 | パック側で壊れていたこと | 対処 |
|---|---|---|
| `acl` / `aclv6` shape 追加（mixed のルーレットにも組込済・紙面専用で実機不要） | なし（そのまま出せる） | 必須ジャンル `acl` として選べるように |
| **複数選択**（「2つを選択してください」13問・正解 `**B・D**` 12件） | **解答フォームがラジオで1つしか選べず解答不能**／JS が先頭1つしか保存・復元しない | 設問文から選択数を読み（`pick_count()`）、2つ以上ならチェックボックス＋「2つ選択」明示。JS は全選択を `B・D` 形式で保存・復元 |
| **7〜9択の問題**（12問・正解が `**H**` `**I**` のものが3件） | `key_of` / `choice_of` が `[A-F]` 固定で、**G 以降を「正解記号を読めず」として無言で採点対象外**にしていた | 記号範囲を `A-J` に拡張。`answers/` 全件でキーが読めることを確認（読めない 0 件） |

※ 採点ロジックの複数選択対応（`choice_of` / `key_of` の集合化）は**別セッションが
先に入れていた**。こちらの修正が二重実装にならないよう、共有ファイルへの変更は
「一致しなければ失敗する」方式で当てること（`.replace()` の空振りに気づけない）。

## 6.7 ★並行セッションとの競合（2026-08-12 実被害）

**作問セッションとパック生成セッションは並行して動く。** この前提を落とすと
資産を取り違える。実際に起きたこと:

紙面の調達は「生成の前後で `questions/` をグロブし、増えたファイル＝自分の成果」と
判定していた。18問のパックを 31 分かけて生成している最中に、別セッションが
新 shape `bgpbest` の問題を1問生成 → **それを自分の成果として取り込み**、
代わりに自分が生成した1問がパックから溢れた（`累計 19/18 問` が兆候）。

- **対処**: 帰属は**生成器の標準出力 `wrote questions/<stamp>.md`** で判定する
  （`_run_paper_gen()`）。他セッションが同時に作っても巻き込まない。
  出力書式が変わって特定できない場合は警告を出す（黙って差分に戻らない）。
- **教訓**: 共有ディレクトリ（`questions/` `answers/` `problems/`）に対する
  「前後の差分＝自分の成果」という判定は、この構成では**常に誤り**。
  実行主体が自己申告する情報だけを信じること。

同種の注意はコードにもある: `gen_instance()` は `problems/` の差分で生成された
問題を特定している（複数増えたら警告して先頭を採用）。ラボ生成は所要が短く
競合の窓が狭いが、原理的には同じ弱さを持つ。
