# M6 追補 — BGP の運用機能の部品と流れ

この追補では、BGP の運用機能を扱います。予備の経路を前もって配っておくこと、外の AS とのセッションを守ること、
受け取る経路を絞ることです。CCNP Service Provider のブループリント(SPCOR)では、2.4 の BGP の実装のうち 2.4.g の追加パスと
2.4.h の PIC、1.5 のコントロール プレーンのセキュリティのうち 1.5.b の BGP の TTL セキュリティとプロトコル認証と、1.5.c の
BGP プレフィックスの抑制にあたります。

M6 では、IOS XR での BGP の組み立て方(アドレス ファミリの階層、ループバックの間の iBGP と next-hop-self、ルート ポリシー、
テンプレート、パスの見方)を扱いました。経路数の上限(`maximum-prefix`)は、テンプレートの例とコマンドの対応表に出てきただけです。
この追補は、その上で、何かが壊れたときと、外から余計なものが来たときの話をします。

1.5.c の語は Cisco の文書に定義が見当たらないので、この追補では、経路数の上限、ダンプニング、集約によるより詳細な経路の
抑制、の 3 つとして扱います(IOS XE の `bgp suppress-inactive` は付録)。追補は 3 つのページと付録に分かれています。

| ページ | 中身 | 課題 |
|---|---|---|
| このページ | 予備の道が届くまでと PE2 が落ちた瞬間を 1 枚の図で追う、それで答えが出る 3 つの問い、用語と部品、部品ごとの設定の場所 | — |
| 予備の道を配る: 追加パスと PIC | ルート リフレクタが最良しか反射しないこと、追加パスとパス ID、予備の経路を CEF に入れる PIC、VPN ラベルの無い網での予備の出口 | M6-5、M6-6 |
| セッションを守る: GTSM と TCP-AO | TTL で隣を見分ける GTSM、MD5 認証、キー チェーンと TCP-AO、IOS XE との組み合わせ | M6-7、M6-8 |
| 受け取りすぎない: 経路数の上限、ダンプニング、集約 | maximum-prefix と上限を超えたときの動き、ダンプニングのペナルティと半減期、集約と summary-only・suppress-route | M6-9、M6-10 |
| 付録 | best-external と VPN、PIC Core と PIC Edge、IOS XRd と IOS XRv 9000 の差、IOS XE の `bgp suppress-inactive`、既定値とコマンドの対応、公式文書と実機の食い違い | — |

ラボは XRT-17 です。AS 65000 のプロバイダーが、顧客の CE1(AS 65001)から AS 65100 の中の宛先 T(203.0.113.1)へ
パケットを運びます。AS 65100 への出口は、X1 とつながる PE2 と、X2 とつながる PE3 の 2 つです。PE1 は IOS XRv 9000 26.1.1、
PE2、PE3、P1、RR1 は IOS XRd 26.1.1 です。CE1、X1、X2、T は IOS XE 17.15(IOL)です。

AS 65000 の 5 台は IS-IS(インスタンス `CORE`、レベル 2)を動かし、コアのリンクでは LDP も動いています。P1 は BGP を
動かしません。PE1、PE2、PE3 は RR1 のクライアントで、RR1 は道の外に置いた専用のルート リフレクタです。PE2 は X1 から
学習した経路のローカル プリファレンスを 200 にするので、主の出口は PE2、予備の出口は PE3 です。

PE1 だけが IOS XRv 9000 なのは、PIC の切り替えを通信で確かめるためです。IOS XRd の入口は予備の経路を CEF に正しく表示しますが、
この仮想機では、遠くの PE が IGP から消えたときにその予備を使わず、BGP を待ちました(付録)。

運用機能では、追加パス・パス ID・PIC・best-external・GTSM・TCP-AO・キー チェーン・ダンプニングと、用語がまとめて
出てきます。ただ、この盤面で起きていることは 2 つです。予備の出口の経路が入口の PE1 まで届き、PE2 が落ちたときに
すぐ使われること。外との 3 本のセッションが、それぞれ守られていること。このページでは、まず 1 枚の図でその 2 つを追い
(2.1 節)、3 つの問いに答え(2.2 節)、そのあとで用語を並べます。

## 1. 何が嬉しいのか

### 1.1 困りごと: 出口が 2 つ、外とのセッションが 3 本

CE1 から T へのパケットは、平常時は PE1 → P1 → PE2 → X1 を通ります。203.0.113.0/24 は X1 からも X2 からも届いて
いますが、PE2 が X1 の経路のローカル プリファレンスを 200 にしているので、AS 65000 のどのルータでも PE2 経由が最良です。

PE3 も X2 から同じ経路を学習していますが、PE3 自身の最良は、RR1 から届いた PE2 経由の iBGP の経路です。BGP が相手へ
広告するのは最良の経路だけなので、PE3 は X2 の経路を RR1 へ送りません。RR1 も最良の 1 本しか反射しないので、PE1 が
知っているのは PE2 経由の経路だけです。予備の出口はあるのに、その道を知っているのは PE3 だけです。

PE2 が落ちると、PE1 は BGP が経路を選び直すのを待つしかありません。PE3 が PE2 の経路をあきらめ、X2 の経路を最良にして
RR1 へ広告し、RR1 がそれを PE1 へ反射して、ようやく PE1 は新しい道を手にします。その間、CE1 から T へのパケットは
3 秒ほど捨てられます。どの手順も仕様どおりで、ただ順番に時間がかかります。

外の AS とは、eBGP のセッションが 3 本あります。CE1 と PE1、X1 と PE2、X2 と PE3 です。顧客が設定を誤って大量の経路を
送ってくることもあれば、X1 の顧客の経路(198.51.100.0/24)が消えては戻ることを繰り返すこともあります。BGP のセッションは
TCP の上にあるので、セッションを狙った偽のパケットも届きえます。M6 の設定には、そのどれに対する備えもありません。

### 1.2 この追補で足すもの

足すものは 3 組です。

- **予備の道を配る**(2.4.g、2.4.h)。追加パス(ADD-PATH)で、PE3 の X2 の経路を、最良とは別の 2 本目として RR1 と PE1 へ
  届けます。PIC で、PE1 はその経路を予備としてフォワーディング テーブルに入れておき、PE2 が消えた瞬間に使います。
  PE2 が落ちたときの途切れは 1 秒未満になります。
- **セッションを守る**(1.5.b)。GTSM(TTL セキュリティ)で、届いたパケットの TTL から、遠くから送られたものを捨てます。
  TCP-AO(または MD5 認証)で、TCP のセグメントを鍵で確かめ、鍵を知らない者が作ったセグメントを捨てます。
- **受け取りすぎない**(1.5.c)。maximum-prefix(経路数の上限)で、1 つの相手から受け付ける経路の数を決めます。ダンプニングで、
  フラップを繰り返す経路をしばらく使わずにおきます。集約で、顧客のアドレスを 1 本にまとめ、より詳細な経路を外へ出しません。

追加パスも PIC も、最良の経路は変えません。PE2 経由はそのまま最良で、PE3 経由は控えに回るだけです。

## 2. 盤面の上で

### 2.1 図: 予備の道が届くまでと、PE2 が落ちた瞬間

図の丸数字は、203.0.113.0/24 の予備の経路が PE1 まで届く順(①〜③)、PE2 が落ちたときに起きる順(④〜⑥)、外との
3 本のセッションとその守り(⑦〜⑨)です。iBGP のセッションはループバックの間で張られているので、①②の経路は P1 を
通りますが、P1 は BGP を話さず、パケットとして運ぶだけです。

:::topo
nodes:
  CE1: [0, 1]
  PE1: {at: [1.5, 1], label: "PE1 (入口)"}
  P1: {at: [3.15, 1], label: "P1 (BGP なし)"}
  RR1: {at: [3.15, 2.4], label: "RR1 (RR)"}
  PE2: {at: [4.65, 0], label: "PE2 (主の出口)"}
  PE3: {at: [4.65, 2], label: "PE3 (予備の出口)"}
  X1: [6.25, 0]
  X2: [6.25, 2]
  T: {at: [7.45, 1], kind: host, label: "T"}
links:
  - [CE1, PE1, "⑦ 経路数の\n上限"]
  - [PE1, P1, "③ 2 本を受け取る\n⑤ 予備へ切り替え"]
  - [P1, PE2, "④ 切れる"]
  - [P1, PE3, "① 予備の経路を送る\n⑤ 切り替え後の道"]
  - [P1, RR1, "② 2 本を反射"]
  - [PE2, X1, "⑧ GTSM\nダンプニング\n集約"]
  - [PE3, X2, "⑥ 切り替え後の道\n⑨ TCP-AO、集約"]
  - [X1, T, ""]
  - [X2, T, "⑥"]
  - [X1, X2, ""]
:::

予備の道が届くまで:

- ① PE3 は、X2 から学習した 203.0.113.0/24 を、予備の経路として RR1 へ送ります。追加パスの送信(send)を設定し、送る経路を
  選ぶルート ポリシーで、最良に加えて予備を 1 本広告すると決めます。経路にはパス ID が付くので、受け手は同じプレフィックスの
  2 本目として扱います。
- ② RR1 は追加パスの受信(receive)と送信(send)を設定し、PE2 からの最良と PE3 からの予備の 2 本を、パス ID を付けて
  PE1 へ反射します。
- ③ PE1 は追加パスの受信(receive)を設定して 2 本を受け取り、予備を最良の隣に RIB と CEF へ入れておきます(PIC)。
  最良は PE2 経由のままです。

PE2 が落ちた瞬間:

- ④ PE2 と P1 の間のリンクが落ちます。IS-IS が、PE2 のループバック 10.255.0.2/32 を経路表から消します。
- ⑤ PE1 の CEF は、最良の経路のネクスト ホップ(10.255.0.2)を解決できなくなった時点で、入れてあった予備(ネクスト ホップ
  10.255.0.3)へ切り替えます。BGP が経路を選び直すのを待ちません。
- ⑥ パケットは VPN ラベルの無いただの IP パケットとして PE3 に届き、PE3 は 203.0.113.0/24 を自分の表で引き直します。PE3 の
  最良はまだ PE2 経由の iBGP の経路なので、PE3 も、X2 経由の自分の eBGP の経路を予備として入れておく必要があります。
  入れてあれば、PE3 も同じ瞬間に切り替え、パケットは X2 を通って T に届きます。入口だけ準備しても、出口の表が古いままなら、
  パケットはそこで捨てられます。

外との 3 本のセッション:

- ⑦ CE1–PE1: PE1 は、CE1 から受け付ける経路の数に上限を付けます(maximum-prefix)。上限を超えると、PE1 はセッションを
  切ります。
- ⑧ PE2–X1: PE2 と X1 は GTSM で、受け付ける TTL の下限を決めます。どちらも TTL 255 で送るので、直接つながった相手の
  パケットは 255 のまま届き、遠くから来たパケットはそれより小さい値で届きます。PE2 は X1 から学習した経路にダンプニングを使い、
  顧客のアドレス(192.168.0.0/22)は集約して X1 へ広告します。
- ⑨ PE3–X2: PE3 と X2 は TCP-AO で、TCP のセグメントごとに鍵から計算した MAC を付け、受け取ったセグメントの MAC を
  確かめます。PE3 も、顧客のアドレスを集約して X2 へ広告します。

### 2.2 3 つの問い

図のどの番号も、次の 3 つの問いのどれかに答えています。答えの中に出てくる部品が、次のページから設定するものです。

**2 本目の道は、誰が誰に知らせるのか。** PE3 が RR1 に、RR1 が PE1 に知らせます。追加パスは、経路ごとにパス ID を付けて、
1 つのプレフィックスについて 2 本目以上も送れるようにする仕組みです。能力は向きごとにあり、経路は、送る側が send を、
受ける側が receive を告げた向きにだけ流れます。PE3 は送るだけ、PE1 は受けるだけ、RR1 は両方です。何を送るかは、送る側の
ルート ポリシーが決めます(ページ「予備の道を配る」)。

**PE2 が消えたとき、誰が最初に切り替わるのか。** フォワーディング テーブル(CEF)です。予備が入っていれば、IS-IS が PE2 の
ループバックを消した時点で、CEF はすぐにそちらを使います。BGP はそれより遅く、ネクスト ホップが消えたことを知っても、
経路を選び直す前に next-hop の追跡の遅延を待ちます。IPv4 ユニキャストの既定は、critical が 3 秒です(抜粋)。

```console
RP/0/RP0/CPU0:PE1#show bgp nexthops
...
Gateway Address Family: IPv4 Unicast
...
Critical Trigger Delay: 3000msec
Non-critical Trigger Delay: 10000msec
```

予備が CEF に無ければ、PE1 は BGP の選び直し(この 3 秒と、PE3 から RR1 を通る広告)が終わるまで、T へのパケットを
捨て続けます。PE1 にだけ予備を入れても、⑥の PE3 で同じ待ちが起きるので、途切れは 3 秒ほどのままです。PE3 にも入れると、
0.2 秒ほどになります(ページ「予備の道を配る」)。

**外とのセッションの守りは、それぞれ何を止めるのか。** 5 つの守りは、見ているものも、止めるものも違います。

| 守り | 何を見るか | 何を止めるか |
|---|---|---|
| GTSM | 届いたパケットの TTL | 遠くから送られたパケット(TTL が下限より小さく届く) |
| TCP-AO、MD5 認証 | セグメントごとの MAC やダイジェスト(鍵から計算する) | 鍵を知らない者が作ったセグメント(偽のリセットなど) |
| maximum-prefix | 1 つの相手から受け付けた経路の数 | 決めた数を超える経路。既定ではセッションごと切る |
| ダンプニング | 経路ごとのフラップ(ペナルティ) | フラップを繰り返す経路。しばらく使わず、広告もしない |
| 集約(summary-only) | 集約の範囲に入る経路 | より詳細な経路の広告 |

前の 2 つはセッションを、後ろの 3 つは経路を守ります。GTSM と TCP-AO は両端に設定します。GTSM を片側だけに
入れたときや、TCP-AO の鍵の ID が両端で合わないときは、セッションが確立しません。後ろの 3 つは、設定したルータの中だけで効きます(ページ「セッションを守る」「受け取りすぎない」)。

## 3. 用語と部品

図と問いに出てきた用語を並べます。左の列は、このあとのページで使う言い方です。

| 用語 | 何か |
|---|---|
| 追加パス(ADD-PATH) | 1 つのプレフィックスについて、最良の経路のほかに 2 本目以上も相手へ送る BGP の拡張(RFC 7911)。能力は OPEN メッセージで、アドレス ファミリごとに、送信(send)と受信(receive)の向きを分けて交換する |
| パス ID | 追加パスで送る経路ごとに付ける識別子。同じプレフィックスの別々の経路を、受け手が区別できる(`Received Path ID`、`Local Path ID`) |
| 予備の経路(バックアップ パス) | 最良の経路と同じネクスト ホップを持つ経路をすべて除き、残りから選び直した最良。IOS XR はルート ポリシーの `set path-selection backup 1` で計算する |
| best-external | 自分の最良が iBGP の経路のとき、eBGP で学習した経路の中の最良を iBGP の相手へ広告する機能。Cisco の文書が載せているのは VPN、VRF、ラベル付きユニキャストのアドレス ファミリで、ラベルの無い経路ではループのおそれがあるとしている。この追補では使わない(付録) |
| PIC | 予備の経路を最良の隣にフォワーディング テーブルへ入れておき、最良のネクスト ホップが使えなくなった時点で、プレフィックスの数によらず切り替える仕組み。出口の PE やリンクが落ちたときの PIC Edge と、コアの中の道が変わったときの PIC Core があり、この追補で設定するのは PIC Edge(違いは付録) |
| next-hop の追跡 | BGP がネクスト ホップへの IGP の経路を見張り、変わったら経路選択をやり直す仕組み。やり直す前に遅延(trigger delay)を置く。IOS XR の IPv4 ユニキャストの既定は critical 3 秒、non-critical 10 秒 |
| GTSM(TTL セキュリティ) | 両端が TTL 255 で送り、受け手は TTL が下限より小さいパケットを捨てる仕組み(RFC 5082)。ルータを 1 つ通るたびに TTL が 1 減ることを使う |
| MD5 認証 | TCP のセグメントに、共有のパスワードから計算した MD5 のダイジェストを付ける方式(RFC 2385)。IOS XR はネイバーの `password`、IOS XE は `neighbor … password` |
| TCP-AO | MD5 認証に代わる TCP の認証オプション(RFC 5925)。キー チェーンの鍵とアルゴリズム(AES-128-CMAC-96 など)で MAC を計算する。鍵を切り替えられる |
| キー チェーン | 鍵の一覧。鍵ごとに ID、キー文字列、アルゴリズム、有効期間を持つ |
| KeyID、SendID、ReceiveID | KeyID は、TCP-AO のセグメントが運ぶ鍵の番号。送り手は自分の SendID を入れ、受け手はそれを自分の ReceiveID として探す。自分の SendID は相手の ReceiveID にそろえる |
| maximum-prefix(経路数の上限) | 1 つの相手から受け付ける経路の数の上限と、警告を出すしきい値(既定 75%)。上限を超えると、既定では Cease の通知を送ってセッションを切る |
| ルート フラップ ダンプニング | フラップを繰り返す経路にペナルティを積み、しきい値を超えたら抑制(suppress)して、使わず広告もしない仕組み(RFC 2439) |
| ペナルティ、半減期 | フラップ 1 回ごとに 1000 加わる値と、それが半分に減るまでの時間(既定 15 分) |
| suppress、reuse、最大抑制時間 | 抑制を始めるペナルティ(既定 2000)、抑制を解くペナルティ(既定 750)、抑制を続ける最長の時間(既定は半減期の 4 倍、60 分) |
| 集約(`aggregate-address`) | 範囲の中の経路が BGP の表にあるとき、範囲全体の経路を 1 本作って広告する |
| summary-only、suppress-route | summary-only は、より詳細な経路の広告をすべて止める。suppress-route は、集約のルート ポリシーの中で選んだ経路だけを止める(IOS の suppress-map にあたる) |
| atomic-aggregate | 集約で、より詳細な経路の情報(AS パスなど)が失われたことを示す属性。`as-set` を付けない集約に付く |

## 4. 取り違えやすい点

- **能力は、セッションを張るときにしか交換されない。** 追加パスの send と receive は OPEN メッセージで告げるので、設定を
  足しただけでは、張られているセッションには効きません。張り直すには `clear bgp <ネイバー>` を使います。
  `clear bgp ipv4 unicast <ネイバー>` は後ろに `soft` か `long-lived-stale` を求め、それだけでは `% Incomplete command.` です。
- **send と receive は、ルータごとの向き。** 経路が流れるのは、送る側が send を、受ける側が receive を告げた向きだけです。
  この盤面では、PE3 が send、RR1 が両方、PE1 が receive です。send は能力を告げるだけで、どの経路を送るかは
  `additional-paths selection` のルート ポリシーが決めます。
- **advertise と install。** `set path-selection backup 1` の後ろの `advertise` は予備を相手へ広告し、`install` は予備を自分の
  RIB と CEF に入れます。RR1 は道の外にいるので広告だけ、PE1 は入れるだけ、PE3 は両方です。
- **追加パスと PIC は別の層。** 追加パスはコントロール プレーンの機能で、BGP で相手へ何本送るかを変えます。PIC は
  フォワーディング プレーンの機能で、CEF に何を入れておくかを変えます。PIC は予備になる経路が表にあることを前提にしていて、
  この盤面でそれを PE1 へ届けるのが追加パスです。
- **GTSM の書き方は OS で違う。** IOS XR の `ttl-security` は hop の数を取らず、TTL 255 だけを受け付けます。IOS XE の
  `neighbor … ttl-security hops <n>` は 255−n 以上を受け付けます(`hops 1` なら 254 以上)。送るのはどちらも TTL 255 です。
  IOS XE の文書は送りには効かないと書いていますが、IOS XE 17.15 は 255 で送ります。
- **IOS XR のネイバーの `keychain` は、MD5 認証ではない。** IOS XR で RFC 2385 の MD5 認証にあたるのはネイバーの
  `password` で、IOS XE の `neighbor … password` とつながります。ネイバーの `keychain` は別の方式で、IOS XE の `password` とは
  つながりません。TCP-AO はネイバーの `ao` です。1 つのネイバーに使えるのは、この 3 つのどれか 1 つです。
- **maximum-prefix は、既定では切ったまま。** 上限を超えて切ったセッションは、`restart` を付けていなければ、
  `clear bgp <ネイバー>` まで落ちたままです。`warning-only` は記録だけ、`discard-extra-paths` はセッションを保って超えた分を
  捨てます。上限は守られますが、切ったセッションの経路は全部消えます。
- **ダンプニングは、ピアのリセットを数えない。** ペナルティが加わるのは経路のフラップで、相手とのセッションのリセットで
  経路が消えても加わりません。抑制した経路は、ペナルティが reuse を下回るか、最大抑制時間がたつか、
  `clear bgp ipv4 unicast dampening` で戻ります。
- **summary-only は、より詳細な経路も止める。** `aggregate-address` だけなら、集約した経路と、より詳細な経路の両方を
  広告します。`summary-only` を付けると、より詳細な経路はどの相手にも広告されなくなります(`show bgp` の行頭の `s`)。
  一部だけを止めるなら、集約のルート ポリシーの `suppress-route` です。

## 5. 部品ごとの設定の場所

設定例は次のページからにあり、この表は、どのルータのどこに書くかだけを示します。IOS XR の行は `router bgp 65000` の下、
IOS XE の行は `router bgp 65100` の下です(キー チェーンと IOS XR の `tcp ao` はグローバル)。

| 部品 | ルータ | 書く場所 |
|---|---|---|
| 追加パスの送信 | PE3 | `route-policy`(`set path-selection backup 1 …`)と、`address-family ipv4 unicast` の `additional-paths send`、`additional-paths selection route-policy <名前>` |
| 追加パスの受信と送信 | RR1 | `route-policy`(同上)と、`address-family ipv4 unicast` の `additional-paths receive`、`additional-paths send`、`additional-paths selection route-policy <名前>` |
| 追加パスの受信 | PE1 | `address-family ipv4 unicast` の `additional-paths receive` |
| 予備のインストール(PIC) | PE1、PE3 | `install` を含む `route-policy` を、`address-family ipv4 unicast` の `additional-paths selection route-policy <名前>` で付ける |
| GTSM | PE2 | `neighbor 172.16.2.1` の `ttl-security` |
| GTSM | X1 | `neighbor 172.16.2.254 ttl-security hops <n>` |
| TCP-AO | PE3 | グローバルの `key chain <名前>` → `key <ID>`(キー文字列、アルゴリズム、有効期間)、グローバルの `tcp ao` → `keychain <名前>` → `key <ID> SendID <n> ReceiveID <n>`、`neighbor 172.16.3.1` の `ao <名前> include-tcp-options …` |
| TCP-AO | X2 | グローバルの `key chain <名前> tcp` → `key <ID>`(`send-id`、`recv-id`、キー文字列、アルゴリズム)、`neighbor 172.16.3.254 ao <名前> …` |
| MD5 認証(この盤面では使わない) | — | IOS XR はネイバーの `password`、IOS XE は `neighbor … password` |
| maximum-prefix | PE1 | `neighbor 172.16.1.1` → `address-family ipv4 unicast` の `maximum-prefix <上限> <しきい値 %> …` |
| ダンプニング | PE2 | `address-family ipv4 unicast` の `bgp dampening …` |
| 集約 | PE2、PE3 | `address-family ipv4 unicast` の `aggregate-address <プレフィックス> …` |

IOS XR では、BGP の部品は `router bgp` の中の 3 つの階層のどこかに入ります。セッションを守るものはネイバーの直下、経路の数は
ネイバーのアドレス ファミリ、追加パス・PIC・ダンプニング・集約はプロセスのアドレス ファミリです。M6 で見た置き場の決まり
(セッションの設定はネイバーの直下、経路に関わる設定はアドレス ファミリの下)と同じです。例外は、グローバルに置く
キー チェーンと `tcp ao` くらいです。
