# M14 — マルチキャストの部品と流れ

この単元では、1 本の流れを大勢の受信者へ一度に送ること、つまりマルチキャストを扱います。CCNP Service Provider の
ブループリント(SPCOR)では、4.4 のマルチキャスト サービスの実装にあたります。4.4.a の PIM(PIM-SM、PIM-SSM、PIM-BIDIR、
PIMv6)と、4.4.b の IGMP v1/v2/v3 と MLD です。

M0〜M13 でブループリントを一周しましたが、4.4 はまったく手を付けていない
ただ 1 つの節でした。M14 は、ここから 2 周目を始めます。単元は 3 つのページと付録に分かれています。

IOS XRd の文書(データシートと 26.1.1 のリリース ノート)には、マルチキャストについての記述がありません。この仮想機では、
ファースト ホップ、RP、ラスト ホップ、中継と、ラボで要るどの役でもマルチキャストを転送します。確かめたことは付録に並べます。

マルチキャストでは、IGMP・PIM・RP・共有ツリー・Register・(\*,G)・(S,G)・DR・クエリアと、用語が一度にたくさん出てきます。
ただ、この盤面で起きていることは 1 つだけで、SRC1 の 1 つのチャネルがどうやって RCV2 と RCV3 に届くか、です。このページでは、
まず 1 つのチャネルを盤面の上で追い(2.1 節)、それについての 3 つの問いに答え(2.2 節)、そのあとで用語を並べます。

## 1. 何が嬉しいのか

### 1.1 困りごと: 1 つのチャネル、たくさんのセットトップ ボックス

SRC1 はテレビのチャネルを送ります。一定の速さで途切れずに続くパケットの流れです。RCV2 と RCV3 は、それを見たいと思って
います。本物のネットワークにはセットトップ ボックスが何千台もあり、その多くが同じ時刻に同じチャネルを見ています。

### 1.2 それ以前の手: 受信者ごとに 1 部ずつ

ユニキャストでは、SRC1 はパケットを受信者ごとに 1 部ずつ、その受信者のアドレス宛てに送ります。ヘッドエンドに近いリンクには、
同じパケットが見ている人の数だけ流れます。セットトップ ボックスが 1000 台なら、SRC1 のリンクには同じものが 1000 部です。

### 1.3 答え: どのリンクにも 1 部だけ、頼まれた所にだけ

マルチキャストは、受信者でなくグループ アドレス(IPv4 では 224.0.0.0/4)へ送ります。SRC1 が送るのは 1 部です。ルータは、
受信者への道が分かれる所でだけパケットをコピーします。そのため、どのリンクにも流れるのは多くて 1 部で、受信者へ続かない
リンクにはそもそも流れません。

そのためには、ルータが、受信者がどこにいるかと、送信元からそこへどう届けるかを知っている必要があります。ホストは IGMP
(IPv6 では MLD)で自分のルータに伝え、ルータどうしは PIM でその間のツリーを作ります。頼むのは受信者の側で、ツリーは
受信者から送信元のほうへ伸びていきます。

## 2. 仕組み: 盤面を渡る 1 つのチャネル

### 2.1 図

図は、1 つのチャネル 239.1.1.1 を、SRC1 から RCV2 と RCV3 まで追ったものです。RP は P1 の Loopback0(10.255.0.11)で、
すべてのルータに手で設定してあります。リンクの上の丸数字は、起きる順番です。

  PE4: {at: [5.1, 1.7], label: "PE4 (ラスト ホップ・DR)"}
  PE3: {at: [3.4, 2.9], label: "PE3 (クエリア)"}
  SW1: {at: [5.1, 2.9], label: "SW1"}
  RCV3: {at: [6.8, 2.9], kind: host, label: "RCV3 (受信者)"}

  - [PE1, P1, "③ Register"]

  - {a: P1, b: PE2, label: "② Join  ④ データ\n⑤ Prune", t: 0.42}
  - [P1, PE3, ""]
  - [PE2, PE4, "② ⑤ Join\n④ ⑤ データ"]
  - [PE2, RCV2, "① レポート\n④ ⑤ データ"]
  - [PE3, SW1, ""]

:::

- ① RCV2 と RCV3 が、239.1.1.1 が欲しいと IGMP でレポートします。ACCESS-3 では、RCV3 のレポートを PE3 と PE4 の両方が
  受け取ります。PE3 がクエリア(小さいほうのアドレス、.252)で、PE4 が DR(大きいほうのアドレス、.253)です。動くのは DR です。
- ② ラスト ホップ ルータ(LHR)の PE2 と PE4 が、RP へ向けて (\*,G) の Join を 1 ホップずつ送ります。PE4 から PE2 へ、
  PE2 から P1 へ。途中のルータは、Join が入ってきたインターフェイスを覚えます。そのインターフェイスをつないだものが、
  P1 を根とする共有ツリーです。
- ③ SRC1 が送り始めます。ファースト ホップ ルータ(FHR)の PE1 は、受信者のことを何も知りません。パケットを 1 つずつ
  Register メッセージに包み、ユニキャストで RP へ送ります。
- ④ P1 は Register からパケットを取り出し、共有ツリーに沿って流します。P1 から PE2 へ、PE2 から RCV2 と PE4 へ、PE4 から
  ACCESS-3 へ。
- ⑤ 流れてきたパケットで、PE2 と PE4 は送信元のアドレスを知ります。PE2 から SRC1 への最短の道は、P1 を回る道でなく、
  PE1 との直結のリンクです。PE2 は PE1 へ (S,G) の Join を送り、PE4 は PE2 へ送ります。PE2 は P1 に、共有ツリーの上の
  SRC1 のパケットはもう要らないと伝えます(Prune)。それからは、チャネルは PE1 → PE2 → RCV2 と PE2 → PE4 → RCV3 を流れ、
  P1 はその道から外れます。

### 2.2 図が答える 3 つの問い

どの段階も、3 つの問いのどれかに答えています。答えの中に出てくる部品が、次のページから設定するものです。

**受信者がいると、誰が言うのか。** 受信者自身が、IGMP で言います。グループが欲しいホストは IGMP レポートを LAN へ送り、
ルータはインターフェイスごとに、メンバーのいるグループの表を持ちます(`show igmp groups`)。表を新しく保つため、LAN ごとに
1 台のルータ(クエリア)が、まだメンバーか、と間をあけて問い合わせます。問い合わせの間隔は、ここでは IOS XR も IOS XE も
60 秒です。

2 台のルータが 1 つの LAN にいるときは、アドレスで仕事を分けます。小さいアドレスがクエリアで、大きいアドレス(DR priority が
既定のとき)が DR です。LAN のために上流へ Join を送るのは DR だけです。ACCESS-3 では、この 2 つが別のルータです。
聞く係と、動く係です。

**PE1 が何も知らない受信者を、最初のパケットはどうやって見つけるのか。** RP を通ります。どのルータもそのグループの RP の
アドレスを知っているので、受信者の側と送信元の側は、互いを知らないまま落ち合う場所を持てます。受信者の側のルータは RP へ
向けて Join します。これが共有ツリーで、(\*,G)、「このグループを、どの送信元からでも」です。送信元の側のルータは、最初の
パケットを Register に包んで RP へ送ります。

RP は、ある送信元のパケットを共有ツリーへ流している間、自分でもその送信元へ向けて Join します。パケットが包まれずに
届くようになると、FHR に Register をやめるよう伝えます(Register-Stop)。PE1 が知っておくべきなのは RP の場所で、受信者の
居場所ではありません。

**最初の数パケットのあとで、なぜツリーが変わるのか。** 共有ツリーは RP を通り、RP がいつも最短の道の上にあるとは
限らないからです。PE2 から RP へは CORE-2 を通りますが、SRC1 へは CORE-12 で直接届きます。最初のパケットが届くまで、
PE2 は送信元のアドレスを知らないので、RP へ向けて Join するしかありません。

アドレスが分かると、PE2 は最短パス ツリー、(S,G)、「このグループを、この送信元から」に Join し、その送信元を共有ツリーから
Prune します。IOS XR も IOS XE も、既定では最初のパケットで切り替えます。`spt-threshold infinity` を設定すると、ルータは
共有ツリーに留まります。

PIM-SM では、ルータはグループのパケットを 1 つのインターフェイスでしか受け付けません。送信元へ(エントリが (S,G) のとき)、
または RP へ(エントリが (\*,G) のとき)向かうユニキャストの経路が出ていくインターフェイスです。これが RPF チェックです。
切り替えのあと、PE2 は 2 つのエントリを両方持っていて、パケットを受け付けるインターフェイスがそれぞれ違います(抜粋)。

```console
RP/0/RP0/CPU0:PE2#show mrib route 239.1.1.1
...

  Up: 00:00:44
  Incoming Interface List
    GigabitEthernet0/0/0/1 Flags: A NS, Up: 00:00:44
  Outgoing Interface List
    GigabitEthernet0/0/0/2 Flags: F NS, Up: 00:00:41
    GigabitEthernet0/0/0/3 Flags: F NS LI, Up: 00:00:44

  Up: 00:00:14

    GigabitEthernet0/0/0/0 Flags: A, Up: 00:00:14
  Outgoing Interface List
```

(\*,G) のエントリは、P1 へのリンクである GigabitEthernet0/0/0/1 で受け付けます(`A`)。(S,G) のエントリは、PE1 へのリンクで
ある GigabitEthernet0/0/0/0 で受け付け、PE4 と RCV2 の LAN へ転送します(`F`。`LI` は local interest で、その LAN にメンバーが
いること)。

P1 では、エントリ `(192.168.1.1,239.1.1.1)RPT` の PE2 側のインターフェイスが `off Prune` です。P1 は落ち合う
場所であって、通り道ではありませんでした。

### 2.3 もう 2 つのツリーと、RP の知り方

**SSM。** 送信元特定マルチキャストでは、受信者がグループと一緒に送信元も指定します。それを運べるのが IGMPv3(IPv6 では
MLDv2)です。LHR は送信元へ向けてまっすぐ (S,G) の Join を送り、RP は出てきません。共有ツリーも Register も切り替えも
ありません。

IOS XR は既定で 232.0.0.0/8 を SSM として扱います。IOS XE がそう扱うのは、`ip pim ssm default` を設定するか、
自分で範囲を書いたときだけです。SSM の範囲では、送信元を指定しないレポート(IGMPv1・v2)は捨てられます。

**BIDIR。** 双方向 PIM には共有ツリーしかなく、トラフィックはその上を両方向に流れます。どの送信者からも RP へ向けて上り、
すべての受信者へ下ります。どのルータも (S,G) の状態を持たず、Register も送りません。リンクごとに 1 台のルータ、DF
(designated forwarder)が、RP へ向けての転送とリンクへの転送を受け持ちます。RP への経路がいちばん良いルータです。
会議のように、メンバーの誰もが送るグループに向いています。

**RP のアドレス。** PIM-SM でも BIDIR でも、すべてのルータが、グループごとに同じ RP を当てる必要があります。伝え方は
3 つです。**スタティック**: すべてのルータにアドレスを設定します。**BSR**(標準、PIMv2): 候補 RP が、選ばれた
ブートストラップ ルータ(BSR)へユニキャストで名乗り出て、BSR がその一覧をすべての PIM ルータ(224.0.0.13)へ 1 ホップずつ
広めます。各ルータは一覧から RP を選び、priority の値が小さいものが勝ちます。

**Auto-RP**(Cisco 独自): 候補 RP は 224.0.1.39 で名乗り出て、マッピング エージェントが範囲ごとに 1 つ(アドレスが最も
大きいもの)を選び、224.0.1.40 で知らせます。同じグループについてスタティックの RP と学習した RP が重なると、スタティックに
`override` を付けない限り、学習した RP が勝ちます。

### 2.4 用語を並べる

販売店を通して配る雑誌がほぼ同じ仕組みなので、右の列でたとえます。SRC1 が出版社、セットトップ ボックスが定期購読者、
ルータがその間の販売店と配送センターです。

| 用語 | 何か | 雑誌なら |
|---|---|---|
| グループ アドレス(G) | マルチキャストの流れの宛先。IPv4 では 224.0.0.0/4、IPv6 では FF00::/8 | 雑誌の誌名 |
| 送信元(S) | グループへ送るホスト。SRC1 | 出版社 |
| 受信者 | グループに参加したホスト。RCV2、RCV3 | 定期購読者 |
| IGMP、MLD | ホストと自分のルータの間。この LAN でメンバーのいるグループはどれか | 近所の販売店に、欲しい誌名を伝える |
| クエリア | LAN ごとに 1 台、まだメンバーかを間をあけて問い合わせるルータ | 毎月「まだ要りますか」と聞く販売店 |
| PIM | ルータの間。メンバーから送信元か RP のほうへ、ツリーを作る | 販売店の注文を、上の取次へ順に伝える |
| DR | LAN の受信者のために上流へ Join し、LAN の送信元を Register するルータ | 通りで 1 軒だけ、注文を出す販売店 |
| RP | 受信者の Join と送信元の最初のパケットが落ち合うルータ | 中央の配送センター |
| Register | FHR が、送信元のパケットを包んでユニキャストで RP へ運ぶメッセージ | 最初の数冊を、宅配便で配送センターへ送る |
| (\*,G)、共有ツリー | 「このグループを、どの送信元からでも」の状態。RP を根とするツリー | どの出版社の号でも、配送センターから配る |
| (S,G)、最短パス ツリー | 「このグループを、この送信元から」の状態。送信元を根とするツリー。送信元ツリーとも呼ぶ | 出版社の倉庫から直接配る |
| RPF チェック | パケットは、送信元(か RP)の方向を指すインターフェイスでだけ受け付ける | 配送センターの方角から来た車からだけ受け取る |
| DF(BIDIR) | リンクごとに 1 台、RP へ向けての転送とリンクへの転送を受け持つルータ | 通りごとに 1 軒、雑誌を回す店 |
| BSR、Auto-RP | すべてのルータが RP のアドレスを知るための、2 つの仕組み | 配送センターの場所を、全店に知らせる回覧 |

### 2.5 取り違えやすい部品

- **DR、クエリア、DF。** 同じような LAN の上の 3 つの別々の選出で、同じルータが選ばれるとは限りません。クエリア(IGMP)は
  アドレスが最も小さいルータで、問い合わせるだけです。DR(PIM)は DR priority が最も高く、次にアドレスが最も大きいルータで、
  Join と Register を受け持ちます。DF(BIDIR だけ)は RP への経路がいちばん良いルータで、RP ごと・リンクごとに決まります。
  ACCESS-3 では、PE3 がクエリアで PE4 が DR です。P1 の上の BIDIR の RP については、PE3 が DF です。PE3 は P1 と直結
  していて、PE4 から P1 への道は PE2 を通ります。
- **(\*,G) と (S,G)。** (\*,G) は「このグループを、どの送信元からでも」で、RPF のインターフェイスは RP を向きます。(S,G) は
  「このグループを、この送信元から」で、RPF のインターフェイスは送信元を向きます。PIM-SM は両方を使い、SSM は (S,G)
  だけ、BIDIR は (\*,G) だけを使います。
- **IGMP と PIM。** IGMP はホストとその LAN のルータの間、PIM はルータの間で動きます。ルータはホストの側へ IGMP を、ほかの
  ルータの側へ PIM を話します。IOS XR では、1 つのコマンドでインターフェイスに両方が乗ります。
- **RP と送信元。** RP は、すべてのルータが合意しているルータのアドレスで、チャネルの送り手ではありません。既定の切り替えでは、
  RP がチャネルを運ぶのは最初の数パケットだけで、SSM には RP そのものがありません。

### 2.6 押さえどころ

- 頼むのは受信者で、ルータは受信者から送り手のほうへツリーを作る。IGMP(IPv6 では MLD)はホストと自分のルータの間、PIM は
  ルータの間。
- PIM-SM では、受信者の側のルータが RP へ向けて Join し((\*,G)、共有ツリー)、送信元の側のルータが最初のパケットを
  Register に包んで RP へ送る。RP はこの 2 つが落ち合う場所。
- 最初の数パケットのあと、LHR は送信元へ直接 Join し((S,G)、最短パス ツリー)、共有ツリーからその送信元を Prune する。
  IOS XR も IOS XE も既定でそうする。
- ルータは、グループのパケットを送信元か RP の方向のインターフェイスでだけ受け付ける(RPF チェック)。
- 2 台のルータがいる LAN では、アドレスの最も小さいルータが IGMP のクエリア、最も大きいルータが PIM の DR。Join するのは DR。
- SSM: 受信者が送信元を指定し、RP はない。BIDIR: 1 本の共有ツリーを両方向に使い、リンクごとに DF がいて、(S,G) はない。
- どのルータも、RP のアドレスを設定(スタティック)か BSR か Auto-RP で知る。

## 3. 組む: 部品ごとの設定の場所

### 3.1 IOS XR と IOS XE での置き場

IOS XR では、マルチキャストを 3 つの塊で設定し、最初の塊が、ほかの 2 つの効くインターフェイスを決めます。IOS XE では、
同じ部品がグローバルのコマンドとインターフェイスのコマンドです。設定例は次のページからにあり、この表は、どこを見るかだけを
示します。

| 部品 | IOS XR | IOS XE |
|---|---|---|
| インターフェイスのマルチキャスト ルーティング(PIM と IGMP が乗る) | `multicast-routing` → `address-family ipv4` → `interface all enable`、または 1 つのインターフェイス | `ip multicast-routing` と、インターフェイスごとの `ip pim sparse-mode` |
| RP と、どのグループをどう扱うか: スタティック RP、SSM の範囲、BIDIR、最短パス ツリーへの切り替え、BSR、Auto-RP | `router pim` → `address-family ipv4` | グローバルのコマンド: `ip pim rp-address`、`ip pim ssm default` か `range`、`ip pim bidir-enable`、`ip pim spt-threshold`、`ip pim bsr-candidate`、`ip pim rp-candidate`、`ip pim send-rp-announce`、`ip pim send-rp-discovery` |
| 1 つのインターフェイスの PIM: DR priority、PIM を止める | `router pim` → `address-family ipv4` → `interface <if>` | インターフェイスの `ip pim dr-priority` |
| 1 つのインターフェイスの IGMP: バージョン、ルータ自身がメンバーになる、スタティックのグループ | `router igmp` → `interface <if>` | インターフェイスの `ip igmp version`、`ip igmp join-group`、`ip igmp static-group` |
| IPv6 | 同じ塊の `address-family ipv6`。MLD は `router mld` の下 | `ipv6 multicast-routing`、`ipv6 pim rp-address`。インターフェイスの `ipv6 mld …` |
| これらのコマンドが参照するグループの一覧 | `ipv4 access-list <名前>`。行は `permit ipv4 239.2.0.0 0.0.255.255 any` など | `access-list <番号> permit 239.2.0.0 0.0.255.255` |

IOS XR では、`multicast-routing` の下の `interface all enable` で、Loopback0 も含むすべてのインターフェイスに PIM と IGMP
バージョン 3 が乗ります。`router pim` と `router igmp` には、振る舞いを変えたいインターフェイスがない限り、`interface` の行は
要りません。

逆は成り立ちません。RP だけを書いた `router pim` では、どのインターフェイスも有効にならず、`show pim interface` は
`No interfaces found for VRF default.` とだけ答えます。

ホストの SRC1、RCV2、RCV3 は、確かめるためにグループに参加して送るだけです。ページの設定例は、課題とは別の値を使います。
